### Phase 12a — Purchase photos

- **Photos on Purchases via the existing `Attachment` (then `Bill`) table — discriminator-only reuse (Phase 12a).** Phase 12a adds gallery photo attachments to Purchases. The locked decision was: extend `ATTACHED_TO_TYPES` with a new `PURCHASE_PHOTO` value rather than (a) creating a parallel `Attachment` table, or (b) renaming `Bill → Attachment` (the latter happened anyway in the polish session, but conceptually independent). **Why**: the Bill table already encapsulates everything needed — R2 key, MIME, size, status state machine, soft-delete, role-aware access via `bill-access.ts`. Adding a new discriminator extends `ATTACHED_TO_TYPES` (one line), `ROLE_MATRIX` (one line), and the photo-specific MIME allowlist (`PHOTO_MIME_TYPES`, excludes PDF) — zero schema changes, zero migration. **Trade-off accepted**: the table name "Bill" became semantically misleading (it stored invoice receipts AND visual photos); resolved in polish session via Bill → Attachment rename. **Rejected alternative — new `Attachment` table**: would have duplicated 80% of the Bill schema just to get a more accurate name; the polymorphism is what the discriminator pattern already solves.

- **Photos attach to parent Purchase, not per-line-item (Phase 12a).** Workshop workflow is "photograph the receipt + the goods collectively" — there's no per-item lens. Per-line-item photos would have added a `PURCHASE_LINE_ITEM_PHOTO` discriminator + per-line gallery + per-line photo count badge, all for no captured workflow value. If a use case emerges where one line item needs distinct visual evidence (e.g., disputed quality on a specific SKU), revisit with a `PURCHASE_LINE_ITEM_PHOTO` discriminator + add a gallery section to a line-item-edit modal.

- **Multi-photo gallery (no hard limit) — R2 capacity is the practical ceiling (Phase 12a).** The schema imposes no per-purchase photo limit. R2's free-tier 10GB storage at 10MB per photo ≈ 1000 photos before any cost; the workshop's realistic upper bound is 5-10 photos per purchase × ~100 purchases/month × 12 months ≈ 12000 photos in year one (still under cost threshold given typical photo sizes <2MB). **If we ever cross the free tier**: either compress/resize on upload (server-side or client-side) or enforce a per-purchase soft limit (e.g., "Max 10 photos per purchase" client-side warning + server hard limit).

- **Create-mode photos use a collect-then-batch pattern; edit-mode uses immediate uploads (Phase 12a).** In **create mode**, the form holds `pendingPhotos: File[]` locally + renders thumbnails via `URL.createObjectURL`. On save, the chain runs sequentially per photo: `prepareUpload(PURCHASE_PHOTO, savedPurchaseId) → R2 PUT → confirmUpload`. Failures of individual photos surface in a banner but don't block the form (the purchase row stays saved). In **edit mode**, `<PhotoGallery mode="edit">` self-loads + uploads/deletes immediately — no pending state on the form. **Why hybrid**: create mode needs the purchase id to attach to (chicken-and-egg), so photos must collect locally + commit after `createPurchase` returns. Edit mode already has an id, so direct uploads are simpler and give immediate feedback. **Rejected alternative — require save first then enable photos**: would have forced a two-step UX for new purchases that breaks the "everything in one form save" pattern established by Phase 10's bill-in-form retrofit.

### Phase 12c — Sales photos

- **Sale photos via SALE_PHOTO discriminator — pure mirror of Phase 12a (Phase 12c).** The same Attachment-table-with-discriminator pattern that solved Purchase photos in Phase 12a extends to Sales by adding one allowlist value (`SALE_PHOTO`), one ROLE_MATRIX row (ADMIN-only, mirroring SALE's read access), one prop-union extension (`PhotoGallery`'s `entityType: "PURCHASE_PHOTO" | "SALE_PHOTO"`), and one options arg on `serializeSale` (`{ photoCount?: number }`). **Zero schema changes, zero migration**: the polymorphic-via-discriminator pattern already absorbed all of Phase 12c's needs. **Code-volume vs infrastructure-reuse ratio**: smallest phase by net source code (Sales side: ~250 LOC across sale-form / sale-detail-modal / sales-table / sale-helpers / page.tsx; Attachment side: 3 single-line additions), largest by infrastructure reuse (PhotoGallery, PhotoLightbox, prepare/confirm chain, presigned URL flow, soft-delete, mobile responsive layout, access matrix, attachment-access lookups — all unchanged). **Rejected alternative — separate `SalePhoto` table or new component pair**: would have duplicated 80%+ of the Phase 12a infrastructure for zero gained semantics. **Rejected alternative — combine `PURCHASE_PHOTO` and `SALE_PHOTO` into a generic `ENTITY_PHOTO` with a separate `entityKind` column**: extra column for a problem the discriminator already solves; harder to query "all photos attached to entity X" via the existing `@@index([attachedToType, attachedToId])`. The mirror-only-add pattern keeps the discriminator's identity stable. **Real-usage-friction validation**: when the workshop owner asked for "photos on sales too — I want to remember which ring went where" near the Phase 12a closeout, the implementation was ~1.5 hours to mirror.

- **Sale photo access is ADMIN-only — inherits the SALE matrix (Phase 12c).** `SALE_PHOTO` in `ROLE_MATRIX` (read) and `WRITE_MATRIX` (mutate) both map to `["ADMIN"]`, matching `SALE` itself. **Why no role expansion**: Sales are an owner-only book (per the Phase 5 RBAC decision); attaching photos doesn't change who can see the sale, so photos inherit the parent's matrix automatically. **Rejected alternative — give `LABOUR_MGMT` photo-only read access** ("the karigar should see what they made"): would have added a non-trivial access path with no corresponding workflow signal; the karigar's mental model is per-piece counts not per-sale lookup. If a "show me sales of the items I worked on" UX surfaces later, the right shape is a karigar-facing view that queries from PieceEntry → Sale association, not a role-flag expansion on SALE_PHOTO.

### Phase 17a — Party unification

- **Party unification via role flags, not enum array (Phase 17a).** Customer / Supplier / CastingPlatingVendor merged into a single `Party` table with four boolean flags (`isCustomer`, `isSupplier`, `isCastingVendor`, `isPlatingVendor`). **Rejected alternative — Postgres enum array column** (`roles ARRAY OF Role`): would have required `roles @> ARRAY['CUSTOMER']` containment queries for every list-by-role page, which Prisma's typed query API expresses awkwardly; the boolean-flag shape gives clean `where: { isCustomer: true }` filtering, indexable per role, and zero raw-SQL escape hatches. The flag count is bounded by the workshop's actual role taxonomy (~4–6 max even with future "polishing vendor" / "welding vendor" additions); the enum-array's upside (extensibility without schema change) doesn't outweigh the query ergonomic loss at this scale. **Casting/Plating flags split intentionally**, even though the Phase 9 `CastingPlatingVendor` model didn't distinguish — real workshops often do one but not the other, and the migration sets both flags on existing rows (matching the prior model's semantics) while leaving future walk-ins to set only the form-context flag. **Phone is globally unique** across Party (`@unique` on the column) so the migration consolidates rows sharing a phone into a single Party with all relevant flags set, and walk-in auto-promotion uses phone as the single identity anchor across all four forms.

- **Walk-in auto-promotion implicit role from form context (Phase 17a).** The four transactional forms (`/sales/new`, `/purchases/new`, `/casting/new`, `/plating/new`) each set a different role flag during walk-in auto-promotion: `isCustomer` on sales, `isSupplier` on purchases, `isCastingVendor` on casting, `isPlatingVendor` on plating. The walk-in input form has no "Is this a customer / supplier / vendor?" question — the form's URL implies the role. **Phone collision behavior**: if the Party already exists at the typed phone, the existing row gets the new flag added (rather than duplicating). The action looks up by phone first; if found and the appropriate role flag is missing, flips the flag inside the transaction. If the user explicitly picks an existing Party from the picker dropdown that doesn't have the matching role flag, the action ALSO flips the flag (e.g., a Party first created as a Supplier picked from the Sales form gets `isCustomer: true` added). All inside `prisma.$transaction`. **Rejected alternative — require explicit role selection on walk-in form**: would add a click for the common case (`/sales/new` always means customer); the form context is enough. **Rejected alternative — never flip flags on existing parties**: would force the user to manually edit a Party to add a role, breaking the "type the phone, it just works" UX.

- **Master data route names preserved (Phase 17a).** `/customers`, `/suppliers`, `/vendors` remain after the Party unification — each page queries Party filtered by the matching role flag. The user-facing UI labels (page titles "Customers" / "Suppliers" / "Vendors", picker placeholders "Customer name or walk-in" etc.) preserved verbatim. **Rejected alternative — single `/parties` unified page**: muscle memory ("/customers shows my customers") was the dominant constraint; users don't think about the data unification, they think about the role. If a unified party admin view becomes useful later, it can be added at `/parties` without disturbing the existing routes. **Type imports aliased** (`import type { Party as Customer } from "@/generated/prisma"`) so existing UI code keeps its descriptive local type names. The Party type structurally satisfies all three legacy types.

### Phase 17b — Payables/Receivables UI

- **Party-rollup as the primary payables/receivables view (Phase 17b).** `/payables` and `/receivables` default to a one-row-per-party rollup with the summed outstanding amount across all in-scope transactions; the per-party detail page (`/payables/[partyId]`) is one click away when the user wants to see the underlying transactions. **Rejected alternative — transaction-list-first view** ("unpaid Bill #142, unpaid Bill #156, etc."): matches the bookkeeping mental model but not the user's. The workshop user thinks "I owe Ramesh ₹30,000" not "I owe Ramesh ₹15k on Bill #142 + ₹15k on Bill #156." Party-first matches that mental model; one extra click surfaces the bill-level breakdown when needed (e.g., to decide which to settle first).

- **Bulk party-level payment with user-picked allocation (Phase 17b).** `<PartyPaymentModal>` lists all unpaid transactions for the chosen party and lets the user check the ones to pay + edit per-row amounts; the sum is the actual payment value. **Rejected alternative — FIFO auto-allocate**: typing "₹20,000" and having the system auto-apply to oldest-first transactions is faster but loses transparency. The accountant needs to see "which bill am I paying right now" to reconcile with the supplier's invoice; auto-allocation forces a follow-up "what just got paid?" UX step. User-picked is the bookkeeping-correct shape. The bulk action `createPartyPayment` runs all `*Payment.create` calls inside one `prisma.$transaction` — if any single create fails, all roll back. Per-allocation validation rejects over-allocation with `errors.allocations[i]` so the modal can surface the error on the failing row rather than a generic banner.

- **Role-scoped payables, ADMIN-only receivables (Phase 17b).** `/payables` access matrix matches the Phase 5 RBAC principle (each role sees the slice of data its workflow touches): ADMIN sees all sources unified, PURCHASE_DEPT sees only purchase payables, CASTING_PLATING_MGMT sees only casting+plating payables, LABOUR_MGMT has no access. `/receivables` is ADMIN-only because the customer-facing book is the owner's concern, not departmental. Defense-in-depth at three layers: (a) proxy `ROUTE_ROLES` gate at URL level; (b) page server-component re-checks via `canViewPayables(role, scope)` / `canViewReceivables(role)` and redirects to /dashboard if denied (catches deep links + URL hacks that bypass the proxy via internal navigation); (c) `createPartyPayment` server action gates by role-intersection across all allocation entity types (a mixed sale+purchase bulk requires ADMIN role since that's the only role in both `SALE`'s and `PURCHASE`'s allowed sets).

### Phase 18 — Labour management

- **Piece entries as a flat model — no `jobType` discriminator (Phase 18).** `PieceEntry` is `{employeeId, date, count, ratePerPiece, totalAmount, note}`. The natural extension — distinct piece-rate jobs per LABOUR worker (e.g. "ear-stud assembly @₹40/piece" vs "necklace finishing @₹60/piece") — would add a `jobType` column to discriminate. **Rejected for Phase 18** because (a) the workshop owner described daily piece tracking as a single per-employee rate workflow, and (b) starting with a discriminator that has only one value forces a UX decision (default value? required selection?) that adds friction without payoff. **Extension shape if needed later**: add `jobType String?` to `PieceEntry`, migrate existing rows to a default value, extend bulk-piece-entry form with a job-type picker per row (or sticky-default at the form level), update `getOutstandingWages` if jobs ever require different payment-tracking semantics. Adding `jobType` is a single migration + a small form change; the rest of the pipeline (`computeOutstandingWages` etc.) doesn't care because outstanding aggregation is per-employee, not per-job-type.

- **Bulk piece entry UX optimised for end-of-day workflow (Phase 18).** The `/labour` page Section 3 is a single-screen form: one row per active LABOUR employee with pre-filled rate (from `Employee.ratePerPiece`) + count input + live line-total + "Save all" button at the bottom. Zero-count rows skipped client-side AND server-side. **Rejected alternatives**: (a) per-employee modal — kills the daily-batch workflow; (b) Excel-like grid — overengineered for the typical 5–15 active LABOUR employees; (c) save-on-tab-out — accidentally creates rows on misclicks. The current shape lets the user tab through count fields, hit Save all once, and walk away. If the active LABOUR employee count grows past ~25, the single-screen layout may need to introduce a "show only with count >0" filter for readability — but at workshop scale (~5–10 active karigars), the flat list is the right shape.

- **Unified `EmployeePayment` ledger with `type` discriminator instead of separate tables (Phase 18).** `SALARY` (FIXED employees, monthly) and `WAGE` (LABOUR employees, per-period) live in one `employee_payments` table with a `EmployeePaymentType` enum. **Rejected alternatives**: (a) separate `salary_payments` + `wage_payments` tables — fragments the per-employee payment history view (the user always wants chronological mixed-type listing); (b) a `payments` table with a polymorphic `payerType` discriminator — overgeneralises for two cases. Single table with type column is cleanest. **Type-vs-employee-type guard** lives at the action layer (`createEmployeePayment` rejects `SALARY` for LABOUR and `WAGE` for FIXED); the DB doesn't enforce this because the constraint is cross-table and Postgres CHECK constraints can't see across rows. The schema-level superRefine for `periodEnd >= periodStart` is intra-row and DOES live in the schema.

- **Wage payment uses period-overlap calculation, not per-entry paid flag (Phase 18).** Instead of foreign-keying each `PieceEntry` to the `EmployeePayment` that paid it (which would require updating all matching entries on payment), wage coverage is computed as a function: `isPieceEntryCovered(entry, payments) = exists payment where payment.type='WAGE' AND payment.deletedAt IS NULL AND payment.periodStart <= entry.date <= payment.periodEnd`. **Why**: (a) production tracking (PieceEntry rows) stays decoupled from payment tracking (EmployeePayment rows); (b) ad-hoc payment periods are first-class — "pay the past 9 days" doesn't need to know which 9 days are in the DB; (c) soft-deleting a payment unpays everything in its window without per-row updates; (d) corrections via the existing soft-delete-and-recreate audit pattern don't accumulate stale FKs. **Trade-off**: outstanding-wages aggregation is O(entries × payments) at compute time instead of O(entries). At workshop scale (~10 active LABOUR × ~20 unpaid days × a handful of payments = ~few thousand ops) this is fine; the `@@index([employeeId, date, deletedAt])` + the in-memory `for` loops make it sub-millisecond. If the table grows to 100k+ rows per employee, denormalize via a `coveredByPaymentId` cache column with trigger-based invalidation. Not needed at current scale.

- **Per-employee payment modal, not single-click "mark as paid" (Phase 18).** The Pay button in `/labour` Section 1 + Section 2 opens `<EmployeePaymentModal>` with amount + period + paid-date + note pre-filled — user reviews, optionally overrides, then confirms. **Rejected alternative**: single-click "mark this employee paid for current month / earliest unpaid period" that creates the payment with full defaults. **Why explicit**: the audit trail wants every payment to have a deliberate "I paid this amount on this date for this period" record. The friction of the modal is the feature — it prevents accidental click-throughs and ensures the user thinks about whether the pre-filled amount matches what they actually handed over (cash adjustments, partial payments, etc.). For SALARY payments where the amount is fixed, the modal is essentially "click → review → save"; for WAGE payments where rounding/adjustments are common, the modal is where the user keys in the actual paid amount.

### Phase 18.1 — Dynamic per-entry piece rate + Note column

- **Piece rate moved from `Employee.ratePerPiece` (fixed) to per-`PieceEntry` only (dynamic).** Real-usage feedback after Phase 18 shipped: rates vary by **job**, not by **worker**. The same karigar does ear-stud assembly at ₹40/piece on Monday and necklace setting at ₹80/piece on Tuesday. Pre-filling the bulk-entry rate cell from `Employee.ratePerPiece` was useless because the user would override it almost every time. **Removed `Employee.ratePerPiece` column entirely** (migration `20260520_remove_employee_rate_per_piece`); the LABOUR employee form drops the rate input; the bulk-piece-entry form starts with an empty rate cell that the user types per row. `PieceEntry.ratePerPiece` stays — it's now the only piece rate, set per row at write time. **Rejected alternative** — keep the column as a "suggested rate" hint: kept the conceptually-misleading worker attribute around for marginal UX value; removing it forces the right mental model. **Rejected alternative** — add a `jobType` discriminator with per-job rates: still imposes a categorical structure on a workflow where the user thinks in free-form notes. The Phase 18 "no `jobType` discriminator" decision held; instead Phase 18.1 added a free-text Note column.
- **Note column on each bulk-piece-entry row (Phase 18.1).** Each row now carries a per-entry `note` field (saves to existing `PieceEntry.note`, which Phase 18 created but didn't expose in the bulk form). User types a free-form description of the piece work — "polishing — rush order", "setting", "ear-stud assembly" — alongside qty and rate. Surfaces in the employee detail modal pieces history (under each entry row) and in the /completed Payroll tab implicitly (Payroll shows EmployeePayment.note, which is a separate field; piece-entry notes are exposed via the per-employee view). **Why free-text instead of structured `jobType` enum**: the workshop describes work fluidly; categorical job types would either fragment ("setting" vs "ear-stud setting" vs "necklace setting") or stale ("setting" becomes the catch-all). A free-text note costs nothing schema-wise (column already existed) and matches how the user thinks.
- **Lesson: "build, use, correct" is the right loop for UX-heavy phases.** Phase 18's per-worker rate model passed schema review, tests, and the Phase 18 walkthrough. It *felt* right in planning. Real usage corrected it. This is a good template: ship a feature, USE it, then revise based on friction the user actually experienced. The cost of the correction was low (one column drop migration + ~300 lines of code touched) precisely because Phase 18 was modeled carefully — clean removal of an unwanted concept is easy when the concept didn't tangle into everything. Future planning notes: when a field exists "in case the user wants it as a default", validate against the workflow before persisting it on a parent entity. Defaults that are overridden 80%+ of the time are anti-features.

### Phase 19 — Completed transactions

- **Tabbed completed-history view, not sub-routes or one combined list (Phase 19).** `/completed` aggregates the five entity types (Sales / Purchases / Casting / Plating / Payroll) under a single page with one tab each. **Rejected alternative — sub-routes per entity** (`/completed/sales`, `/completed/purchases`, ...): scatters the workflow ("did the work happen this month?") across five URL navigations and forces filter duplication per route. **Rejected alternative — single combined list with a Type column** (Sale / Purchase / Casting / Plating / Payment): forces a least-common-denominator row shape that loses entity-specific columns (line items for sales, materials+weight for casting, employee+period for payroll) — these are NOT cosmetically different, they're the actual point of looking at the row. Tabs let each entity render its own column set while keeping the URL and filter surface unified. **Adding a new entity type** to /completed (if some future entity supports the `completed` status): three things — extend `getCompleted<Entity>` query helper, add a tab to `completed-client.tsx`, ensure the entity has a read-only detail modal. ~30 min.

- **Shared filters across all tabs, not per-tab (Phase 19).** Date range (from/to) + party-or-employee search apply to **every** tab simultaneously — changing the range on the Sales tab updates Purchases/Casting/Plating/Payroll too. **Rejected alternative — per-tab filter state** (each tab remembers its own date range): mismatches the user's mental model ("show me everything that happened in October"). The workshop user thinks calendar-window-first, then drills into entity types within that window. **Implementation**: client component owns from/to/q state, `router.replace`s the URL on filter change; the server page parses search params and re-runs ALL five query helpers with the same filter. Tab switches preserve the filter because the URL stays the same — only the active panel changes locally.

- **Strict status===completed filter for transactional entities; Payroll shows every payment (Phase 19).** Sales/Purchases/Casting/Plating filter rows to `status === 'completed'` (post-`computeTransactionStatus`); `pending`/`partial`/`refund_due` rows are excluded because they're still operationally in-flight — the user works those on the entity-specific page (e.g., `/sales`). Payroll is different: every non-deleted `EmployeePayment` is **inherently** a completed event ("the payment happened, the money moved"). There's no concept of a "partially paid" payment row. So the Payroll tab applies date+employee filters but no status filter. **This asymmetry is correct, not a bug** — the underlying business semantics differ. If a future entity has the same inherently-completed shape (e.g., a hypothetical immutable journal entry), it follows Payroll's pattern.

- **Dedicated read-only tables per tab, not the entity list tables (Phase 19).** The four transactional list tables (`sales-table.tsx`, `purchases-table.tsx`, `casting-table.tsx`, `plating-table.tsx`) bake in mutation UX (inline Pay/Bill/Return action buttons, Edit/Delete row hover actions, internal search input + Add button at the top, internal detail-modal state). **None of those affordances belong on /completed** — completed transactions are settled; adding a Pay button on an already-paid row would be cognitive noise, and the Add button doesn't make sense on an aggregated view. The shared search input also conflicts with /completed's cross-tab unified filter bar. **Decision**: build dedicated read-only tables per entity in `src/app/(app)/completed/completed-*-table.tsx`. They reuse `ResponsiveTable`, `TransactionStatusChip`, format helpers, and the existing read-only detail modals (which are already mutation-free post-Phase 10). **Rejected alternative — refactor the existing list tables to accept a `mode: 'view' | 'manage'` prop**: would have added prop-driven conditional rendering across ~200 LOC × 4 tables for the benefit of avoiding ~150 LOC of dedicated tables × 4. Net LOC is similar; the dedicated tables are simpler to read because they're scoped to one job.

- **Payroll rows non-clickable on initial Phase 19 iteration.** The Payroll tab shows EmployeePayment rows with employee name + type + period + amount + note + paid-on all visible inline. Rows did not open a detail modal in the initial ship. **Why**: there was no `EmployeePaymentDetailModal` in the codebase yet, and reusing the `EmployeeDetailModal` (which fetches full history) was heavier than the workflow needs. Inline-visible fields covered what the user wanted when scanning the payroll log. *Note: a lightweight `PaymentDetailModal` was added in the polish session that followed Phase 19 — see "PaymentDetailModal" resolved entry below.*

### Phase 20 — Print-friendly sales bill + shop settings

- **Sales bill as a print-friendly HTML route, NOT a server-generated PDF (Phase 20).** The bill is rendered as a normal Next.js page (`/sales/[id]/bill`) and printed via the browser's native print dialog (Ctrl+P → paper OR save-as-PDF). **Rejected alternative — server-generated PDF (e.g., `pdfkit`, Puppeteer, Chromium headless)**: would add a heavy dependency, async-job complexity, and a file-artifact lifecycle (where to store generated PDFs? cache? re-generate on settings change?) for what is fundamentally a "print once and hand to the customer" workflow. Browser print is reliable, OS-native, and lets the user choose paper or save-as-PDF without any app code. **Revisit when**: bills need to be stored/emailed/batch-exported. Then a PDF library + storage layer becomes worth the cost.

- **Kaccha bill — no payment status, no bill number (Phase 20).** The print bill renders shop header + date + customer + line items + totals + optional notes/footer. It does NOT show whether the sale is paid/partial/pending, and it does NOT display a sequential invoice number. **Why both excluded**: matches the workshop's existing informal billing tradition. The customer's bill is the "what you bought + what you owe" snapshot, not the shop's internal collection-state log. Bill numbering would suggest formal accounting (GSTR-1 export, audit-ready ledger) which the shop doesn't do — see the kaccha-bill non-feature note above. **If formal numbering is ever required** (GST registration, customer demands a numbered invoice), add a `Sale.billNumber Int @default(autoincrement())` column + render it on the bill. Trivial extension; deferred because the trigger doesn't exist.

- **ShopSettings as single-row config table (Phase 20).** First config entity in the app. The shop's header content (name, phone, address, footer) needs to be admin-editable rather than hardcoded so the workshop owner can adjust without a deploy. Decision shape: a real DB table, not a `.env` value — `.env` would require an admin to SSH into Vercel + redeploy to change. **Single-row enforcement at the application layer** (not via DB constraint). The actions use `findFirst` + create-or-update; no `singleton: 'shop'` unique column or trigger. The brief race window where two admins write simultaneously is acceptable at workshop scale (1–3 concurrent users); a future `prisma.$transaction` wrap could harden if real contention surfaces. **Why DB-singleton vs. file-based config (e.g., a JSON file in R2)**: a DB row is editable from the same Prisma surface every other entity uses; a separate file would require its own read/write surface. Pattern reusable for any future config entity (feature flags, notification preferences). See CLAUDE.md §6 for the "single-row config" convention.

- **"Print Bill" disambiguated from existing "Bill" attachment action (Phase 20).** The app pre-Phase-20 already had a "Bill" action on each sales row — the Paperclip icon that opens the attachment-upload modal for the uploaded INVOICE document (supplier-side). Phase 20 added a SECOND "bill" concept (customer-side, generated receipt). **Rejected alternative — pick one term and overload it**: would have been ambiguous in UI titles, aria labels, and discussion. The two are fundamentally different artifacts: one is the supplier's invoice scan attached to the sale (Phase 8 attachment workflow), the other is the receipt printed for the customer (Phase 20). **Resolution**: keep both, but rename the existing one to "Manage invoice attachment" (Paperclip stays as the icon), add the new one as "Print bill" (Printer icon). Leading verb + icon + UX target (modal vs new tab) carry the distinction. **Pattern**: when adding a feature that overloads an existing term, prefer renaming the EXISTING usage to be more specific rather than letting two distinct things share a label. Documented as a convention in CLAUDE.md §6.

- **Bill reads ShopSettings LIVE, not snapshotted at sale time (Phase 20).** When an admin edits the shop name or footer, every existing bill reflects the new value on next render — there's no `sale.shopHeaderSnapshot` column. **Why live**: matches the workshop's mental model. The shop header is a branding decision, not a per-sale fact. If the shop renames itself or moves, the admin expects ALL future printings (including reprints of old sales) to use the new identity. **Trade-off considered**: if the shop ever needed legally-accurate "this bill as printed on date X showed name Y" reproducibility (e.g., for an audit trail of historical brand), a snapshot would matter — but kaccha tradition + workshop scale makes this irrelevant. Walkthrough Step 9 pins the live-read behavior. **Revisit if** legal/audit requirements ever demand frozen-at-time-of-issue billing.

- **Print route via sibling `(print)/` route group, not a layout-skip flag (Phase 20).** The (app)/ layout wraps children with Sidebar + main. A deeper layout.tsx (e.g., `(app)/sales/[id]/bill/layout.tsx`) can't unwrap from the parent. **Rejected alternative — render-time conditional via a `noChrome` prop or pathname check in (app)/layout.tsx**: scatters layout logic across the file, adds a flag every print route would need to set, and makes the sidebar's presence dependent on URL parsing instead of file-tree structure. **Resolution**: sibling route group `(print)/` with its own layout that omits the sidebar. URLs don't collide because route groups don't affect URL paths. Body background overridden via inline `<style>` because the cream `body { background-color: var(--color-surface) }` from globals.css would otherwise leak through. Pattern reusable for any future print/export route. Documented as a convention in CLAUDE.md §6.

### Phase 16 — User management UI

- **Single-role-per-user retained; Phase 5.5 multi-permission refactor dropped (Phase 16).** The existing four-role model (`ADMIN | PURCHASE_DEPT | LABOUR_MGMT | CASTING_PLATING_MGMT`) is the access matrix. A user has exactly one role. **Rejected alternative**: refactor to a permission-bag model (`["view_sales", "edit_purchases", ...]`) for fine-grained access. **Why kept simple**: at workshop scale (4 users today, maybe 8–10 ever) the role count is small, the access boundaries align with job functions cleanly, and the audit lineage stays trivial ("Pat is PURCHASE_DEPT, so they can/can't see X"). The multi-permission refactor (originally tagged Phase 5.5) was always conditional — only if real role conflicts emerged. They didn't. Phase 16's UI just CRUDs the existing model.

- **Soft-delete via `deletedAt` (NOT `isActive` Boolean) (Phase 16).** Matches every other entity's convention. **Why important**: the soft-delete pattern is the load-bearing invariant that lets us preserve `createdById` / `updatedById` / `deletedById` audit FKs across Party, PieceEntry, EmployeePayment, Attachment. Hard-deleting a user would either fail (ON DELETE NO ACTION) or null out historical attribution (ON DELETE SET NULL — defensible but loses "who created this record" forever). Soft-delete keeps the row, keeps the FKs valid, and lets `authorizeCredentials` reject logins via a single `deletedAt IS NOT NULL` check. **Rejected `isActive` Boolean**: would have been one MORE convention in the codebase; the rest of the app already speaks `deletedAt`.

- **Admin-set passwords + out-of-band communication; no email infra (Phase 16).** When an admin creates a user OR resets their password, the admin types the new value in the form and is responsible for relaying it to the user (in person, over phone, via the workshop's chat group). **Rejected alternative — email invite/reset link flow**: requires SMTP infra, deliverability monitoring, secret-token table, time-bound link verification, leaked-link handling. Not worth building for a 1–3 user internal app. **Trade-off accepted**: the brief window between password generation and out-of-band communication is the threat surface. Mitigated by (a) admin sets memorable-ish passwords manually, (b) workshop is small + co-located, (c) MIN_PASSWORD_LENGTH = 8 + bcrypt cost 12 raises the offline-attack bar. **Revisit if user count grows or if a remote-worker scenario emerges** — at which point an email-invite phase (~1 day) becomes reasonable.

- **Forced password-change-on-first-login deferred (Phase 16).** A user logs in with the password the admin set; the system does NOT force them to change it. **Why deferred**: optional security hardening; no incident or feedback prompted it. **Trade-off**: an admin who reuses a password format (or a user who never changes the admin-set value) keeps that value in service. The shop's small user count makes this an acceptable risk for now. **Implementation shape when needed**: add `mustChangePassword Boolean @default(false)` to `User`, set true on create/reset, add a `/auth/change-password` redirect from middleware when `mustChangePassword=true`, clear the flag on successful change. ~1 day. **Revisit when self-service settings UI lands.**

- **Three self-protection guardrails enforced server-side AND mirrored in UI (Phase 16).** G1 (no self-deactivate), G2 (no self-demote), G3 (always ≥1 active admin). **Why three layers — action+UI+test:** UI alone is bypassable (devtools, direct fetch); server alone is correct but offers bad UX (user clicks button, server says no, user re-clicks confused); test alone proves logic but doesn't prevent regressions. All three pin the contract from a different angle. **Rejected alternative — UI gating only**: would technically let a malicious admin remove themselves via crafted fetch. The G3 case is the most consequential — without it, the production app would be permanently lockable if an admin deactivated themselves and the count happened to drop to zero. The action-layer guard runs a fresh `prisma.user.count` inside the operation so race conditions between two admins simultaneously deactivating a third can't both succeed. **Rejected alternative — DB-level CHECK constraint for "≥1 active admin"**: Postgres CHECK constraints can't see across rows. A trigger could enforce, but the trigger would either ABORT the transaction (matching the action's behavior) or silently allow an inconsistent state — both worse than an application-layer guard with a user-visible error message.

- **`UserForClient` strips `passwordHash` via explicit destructure (Phase 16).** `serializeUser` builds the client-safe shape by enumerating every property by name rather than `const {passwordHash: _, ...rest} = u`. **Why**: future User-shape additions (a `mustChangePassword` flag, a `lastLoginAt`, anything sensitive) need to be a conscious decision to include or exclude. The `...rest` pattern would silently propagate the new field; the explicit pattern forces a rebuild of `serializeUser`. **Same reasoning applies to any client-facing serializer that handles security-relevant fields.** Pattern established Phase 16.

- **`authorizeCredentials` extracted to its own module for testability (Phase 16).** `src/lib/auth.ts` originally inlined the authorize callback inside the NextAuth config. Phase 16's auth tests needed to import the function but importing `./auth` transitively pulls in `next-auth` which has a `next/server` resolution issue in the Vitest environment. Solution: move the callback to `src/lib/authorize-credentials.ts` (just bcryptjs + prisma + zod imports). `src/lib/auth.ts` now wraps NextAuth and re-exports `authorizeCredentials` for backward compat. **Rejected alternative — mocking `next-auth` deep**: fragile and would mask future regressions in the deactivation guard. **Pattern**: when a function inside a framework-config file needs unit-test coverage, hoist it into its own module that imports only the libraries it actually uses.

### Polish session (cross-phase)

- **Kaccha-bill model — no GST, HSN codes, or tax handling.** The business operates on informal "kaccha" (literally "raw" / unofficial) bills — the workshop's invoicing tradition, common across small Mumbai jewelry manufacturers. The schema intentionally excludes every tax-related field: no `gstin` on parties, no `gstAmount` / `cgst` / `sgst` / `igst` on transactions, no `hsnCode` on line items. Invoice math is plain rupees throughout: `total = SUM(line.qty × line.rate) − discount`, no tax addition layer. The four-state status machine reflects payment + return state only, not tax-filing state. **Why intentional**: the workshop's customers expect kaccha bills, the workshop's books are kept on the same basis, GST registration is not required at this transaction volume + business structure. Adding tax fields proactively would (a) clutter every form with fields the user would leave blank, (b) introduce display ambiguity ("is this total including or excluding tax?"), (c) suggest the app supports a workflow it doesn't (filing returns, generating GSTR-1, etc.). **If GST adoption ever becomes required** (business restructure, threshold crossed, customer demands), the migration shape is well-understood: add nullable `gstin` to parties, add `gstAmount` / `cgst` / `sgst` (BigInt paise) to transactions, add `hsnCode` to line items, add a tax-inclusive vs tax-exclusive toggle to the invoice math, build a returns-export view. Estimated effort: ~3–4 phases. **Not a deferred item — explicit non-feature.** This entry exists to prevent future contributors from "fixing" the missing-GST appearance and to anchor the schema's plain-rupees invariant.

## Onboarding notes for future contributors

Things that aren't gaps but trip up new sessions.

### Workstation / first-time setup

- **MCP authentication is per-developer.** `.mcp.json` at project root declares the Supabase MCP server, but OAuth tokens are stored in each developer's local Claude Code state — not in the repo. A new session in this folder must run `claude /mcp` in a regular terminal (outside the IDE), select `supabase`, and complete OAuth before MCP tools work. The `.mcp.json` file itself is committed; tokens are not.

- **Dev server default port may be 3001, not 3000.** If another long-running node process holds port 3000, `next dev` falls back to 3001 with a `⚠ Port 3000 is in use` warning. Check the dev.log / terminal output for the actual port before opening the browser. To free port 3000: `Get-Process node` (Windows) or `lsof -i :3000` (mac/linux) → identify the holder → kill it if it's a stale dev server.

- **Supabase keys use the new `sb_publishable_…` / `sb_secret_…` format**, not legacy JWTs. The env var names in `.env.local` retain the legacy `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY` convention from the original spec, but the values are new-format. `@supabase/supabase-js@2.105+` accepts both formats. Don't be surprised that the values don't look like JWTs.

- **DB password contains URL sub-delim characters** (`,` and `*`). It's URL-encoded as `%2C` and `%2A` inside both `DATABASE_URL` and `DIRECT_URL` so Prisma's URL parser doesn't choke. If you regenerate the password and it contains other reserved characters (`+`, `&`, `?`, `#`, `/`, `@`, `:`, space), URL-encode them too.

- **Never `source` / `set -a` `.env*` files that contain URL query strings.** Bash treats unescaped `&` as a background-job operator, silently truncating values like `DATABASE_URL=postgresql://...?pgbouncer=true&connection_limit=1` at the first `&`. The bug is invisible at the script layer — the variable IS set, just to the wrong value. Phase 4.5 hit this exact trap during the initial Vercel env-var upload. **Canonical pattern**: parse env files via Node, not via shell. Either `import { config } from 'dotenv'; config({ path: '.env.production.local' })`, or a one-shot `node -e` script that reads the file with `fs.readFileSync` and a regex.

- **First-time setup after `git clone`.** Required steps before the dev server is useful: (1) `npm install` (runs `postinstall` → `prisma generate` → barrel write); (2) populate `.env.local` from `.env.example`; (3) `npx prisma migrate deploy` to apply existing migrations; (4) `npx prisma db seed` to create the admin user; (5) `npm run dev`; (6) sign in at `/auth/login` with the seeded credentials.

### Build / cache pitfalls

- **Build-cache cousins — `rm -rf .next/` is the universal first-aid kit when "I changed something and the dev server is still serving stale behavior."** Turbopack's compiled chunks under `.next/` can pin to a build's view of env-dependent module evaluation, CSS token resolution, or generated-client shape. Symptoms seen across phases:
  - Tailwind CSS chunk served stale `--spacing-md` mapping after `globals.css` edits
  - Prisma client singleton instantiated before a new model was added
  - Prisma reported `Authentication failed` after a verified-correct DB password change

  **First diagnostic step** when a change to env vars, `globals.css`, `schema.prisma`, or any generated code doesn't take effect after a normal dev-server restart: stop the dev process, `rm -rf .next/`, restart. Saves hours over speculative debugging.

- **Lazy Prisma client construction is required by Next.js 16 build-time page-data collection.** `src/lib/prisma.ts` wraps `PrismaClient` in a `Proxy` so connection-string read + adapter construction defer to first property access. **Do NOT** revert to eager construction. Next.js 16 imports route modules during the "Collecting page data" build phase to extract metadata; eager construction would fire a throw on missing `DATABASE_URL` even when the env IS configured for runtime. See `docs/HANDOFF.md` § 3 and the file's header comment for the canonical lazy-client pattern.

- **R2 / SDK clients also use lazy-init Proxy.** `src/lib/r2.ts` mirrors the Prisma wrapper pattern: env (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, etc.) is read on first property access, not at module load. Any SDK client wrapper that reads env vars at construction time should defer via Proxy.

### Conventions / canonical patterns

- **Tailwind v4 — theme tokens live in `src/app/globals.css`, NOT in a JS config file.** Don't go looking for `tailwind.config.ts` — it doesn't exist. All color/font/radius tokens are defined in the `@theme { … }` block inside `globals.css`. If you need to add a new color or change a token, edit `globals.css`. The `@theme` directive auto-generates Tailwind utility classes (`bg-surface-container`, `text-on-primary`, etc.) and CSS custom properties from the declarations.

- **Currency is stored as integer paise**, not rupees-with-decimals. `₹1,234.56` ↔ `123456` paise. Never store, sum, or arithmetic-on currency as a float anywhere. **Three-layer pipeline**:
  1. **Prisma column:** `BigInt? @map("monthly_salary")` — paise integer math, safe for any salary range.
  2. **Schema:** validates rupees as `z.number().int().positive().nullish()` — wire-format identical on client send and server re-parse. **Do NOT** put a `.transform(v => BigInt(...))` in the schema.
  3. **Action:** a local `toPrismaData()` helper converts rupees → `BigInt(Math.round(value * 100))` paise at the Prisma write only. On return, `serializeEntity()` converts BigInt back to `number` for JSON safety. UI receives `EntityForClient` with `monthlyXxx: number | null` and renders via `formatCurrency(paise)` from `src/lib/format.ts`.

- **Status is derived, not stored.** Don't add a `status` column to `Sale` or `Purchase`. See `CLAUDE.md` §5 for the full rationale and the TypeScript string-literal union pattern.

- **Server/client module-boundary discipline.** Three classes of bug have surfaced from incidental imports crossing the boundary. Before adding a new entity or import, ask "what does this pull along with it?"
  - **Zod schemas exported from `'use server'` files** are compiled into client-reference stubs by Next.js. Keep schemas in `schema.ts` (no directive); actions import the schema.
  - **Type-only exports from `'use server'` files** also break — Next.js's actions loader produces `ReferenceError: TypeName is not defined` at runtime when a client component imports the type. Keep client-facing types and serializer helpers in `types.ts`, not in `actions.ts`.
  - **Prisma enum value imports** (e.g. `import { EmployeeType } from "@/generated/prisma"`) pull `@prisma/client/runtime/client.mjs` (which uses `node:module`) into the client bundle. Use `import type { EmployeeType }` for type-only references; use `z.enum(["FIXED", "LABOUR"])` with literal strings for runtime validation.

  General principle: if a value (not a type) crosses from server-only territory to client-reachable territory, audit its transitive imports for Node-only modules (`node:*`, `pg`, `fs`, `crypto` outside Web Crypto), Next.js server-action stubs, or anything carrying `'use server'`.

- **Schema change workflow.** When adding or modifying a Prisma model:
  1. Edit `prisma/schema.prisma`
  2. `npx prisma migrate dev --name <description>` — applies the migration to the DB via `DIRECT_URL`
  3. `npm run prisma:generate` — Prisma 7 doesn't auto-regenerate after `migrate dev`; this also writes the `src/generated/prisma/index.ts` barrel
  4. **Restart the dev server** — `src/lib/prisma.ts` caches the `PrismaClient` instance in `globalThis.prisma`. New models will be `undefined` on the running singleton until the process restarts.

- **Postgres `anon` and `authenticated` roles have no privileges on the `public` schema.** New tables don't need RLS policies for security (the only roles that can access them are `postgres` / `service_role`, both of which `BYPASSRLS`). Adding RLS as defense-in-depth is fine. If you see "RLS disabled" advisories from Supabase, **the threat is mitigated by the grant revocation**.

- **Prisma client output lives at `src/generated/prisma/` (gitignored).** The directory is regenerated by `npm run prisma:generate`. Never edit files inside it directly. Importing pattern: `import { prisma } from '@/lib/prisma'` for the singleton; `import { PrismaClient, Prisma, $Enums } from '@/generated/prisma'` for type imports.

- **JWT sessions — no DB session table.** Auth.js is configured with `session: { strategy: 'jwt', maxAge: 30 days }`. Sessions are stateless JWE cookies signed/encrypted with `AUTH_SECRET`. There is no `sessions` table in the DB. To invalidate all sessions globally, **rotate `AUTH_SECRET` in `.env.local`** (or in Vercel for prod).

- **Heading fonts cascade from `@layer base`, not from per-element classes.** All `h1`–`h6` elements automatically use Geist via `html, body { font-family: var(--font-sans); }` + `h1, h2, h3, h4, h5, h6 { font-family: var(--font-display); }` in `src/app/globals.css`. **Don't add `font-display` to heading elements** — it's redundant. Only use `font-display` on **non-heading** elements that should look like headings (e.g. the dashboard card's stat number).

- **Tables with Prisma `@updatedAt` — direct-SQL `UPDATE`s via Supabase MCP must set `"updatedAt" = NOW()` explicitly.** Prisma's `@updatedAt` is application-managed (the Prisma client sets the column on every update call), NOT a DB trigger. All app code goes through Prisma and inherits this automatically — but ad-hoc `UPDATE` statements via Supabase MCP `execute_sql` won't touch `updatedAt` unless you include it: `UPDATE users SET role = 'STAFF', "updatedAt" = NOW() WHERE id = '…'`.

- **Per-entity folder convention.** Each CRUD entity lives under `src/app/(app)/<entity>/` with this fixed layout:
  - `page.tsx` — server component, queries the entity list, embeds the client table
  - `schema.ts` — zod validation, **plain TS, no `'use server'` directive**
  - `actions.ts` — `'use server'`, imports the schema, exports `create<Entity>` / `update<Entity>` / `softDelete<Entity>`
  - `<entity>-table.tsx` — client component, TanStack Table v8, search + sort + zebra striping
  - `<entity>-form-modal.tsx` (master data) OR `<entity>-form.tsx` + `/new` / `/[id]/edit` pages (transactional entities — Phase 10+ pattern)
  - `<entity>-detail-modal.tsx` — client component, read-only view

  Soft delete is mandatory: every entity that touches business data gets a nullable `deletedAt` column + an index on it. List queries filter `where: { deletedAt: null }`. Restore is via direct DB UPDATE.

- **Path alias:** `@/*` → `src/*`. No relative `../../` imports across feature boundaries.

### Auth / RBAC

- **Defense in depth for route access** — three layers (proxy `ROUTE_ROLES` URL gate, page server-component redirect, server-action `requireRole(...)` gate). All three required; the matrix is duplicated in three places at acceptable redundancy. If the matrix grows complex enough that drift becomes a real risk, extract to a single source-of-truth and have all three layers consume it. See `src/lib/role-access.ts` for the role-access helpers and `src/proxy.ts` for the URL gate map.

- **`requireRole([...allowedRoles])` is the canonical role gate at every server action.** First await in every action. Throws `Unauthorized` (no session) or `Forbidden` (wrong role). Reading the action's first line tells you the access matrix at a glance. `requireSession()` exists for the (currently zero) cases where any authenticated user is sufficient.

- **Breaking enum migrations in non-interactive contexts.** `prisma migrate dev` requires interactive confirmation for breaking enum changes — the prompt is unskippable. In CI / agent shells / non-TTY contexts, the canonical workaround is: (1) update `prisma/schema.prisma`; (2) generate SQL via `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`; (3) hand-create the migration directory under `prisma/migrations/<timestamp>_<name>/` and paste the SQL into `migration.sql`; (4) apply with `npx prisma migrate deploy`.

### Testing

- **Running tests.** Three scripts:
  - `npm test` — Vitest watch mode for development
  - `npm run test:run` — one-shot run, used by CI / pre-commit hooks
  - `npm run test:coverage` — one-shot with `@vitest/coverage-v8` baseline

  Run a single test file: `npx vitest run path/to/file.test.ts`. Run a single test by name: `npx vitest run -t "rejects empty name"`.

- **Adding a new entity (Phase 2.3 onward).** Each entity must include: `schema.test.ts` (zod-only, no mocks), `actions.test.ts` (mocked Prisma + auth-guards + next/cache), and a component test on the entity's table (`<entity>-table.test.tsx`). Use the Customer/Supplier files as templates.

- **Test count reporting.** The "Test count delta" line in every phase report stops being `N/A`. Format: `<previous total> → <new total> (+N net new, M skipped with reason)`.

- **Test inputs to actions match `z.output<schema>`, not the raw form input shape.** Unit tests bypass the form layer and call the server action directly. The action's exported parameter type is `z.infer<typeof schema>` which equals `z.output` — the post-coercion shape. So test fixtures must construct values matching the OUTPUT, not the pre-coercion FORM shape. Concrete example: `SaleInput.date` is `Date` after `z.coerce.date()`, so `validInput()` must construct `new Date("2026-05-14T00:00:00Z")`, not the form's `"2026-05-14"` string.

- **`fireEvent.focus()` for jsdom React onFocus handlers.** Programmatic `element.focus()` in jsdom does NOT reliably trigger React's synthetic `onFocus`/`onBlur`/`onMouseEnter` handlers. Tests that rely on these handlers firing need explicit React-event dispatch: `fireEvent.focus(input)` or `userEvent.click(input)`.

- **Live-updating modal pattern — detail modals that show mutable data must derive, not snapshot.** When a detail modal exposes inner UI that mutates the entity, do NOT hold the entity as `useState<EntityForClient>(viewing)`. After `router.refresh()` the parent re-fetches but the modal's local state still references the *stale* pre-mutation object. **Canonical pattern**: `useState<string | null>(viewingId)` + derive via `const viewing = viewingId ? parentDataArray.find(x => x.id === viewingId) ?? null : null`. After mutations call `router.refresh()`, the parent re-fetches → the derived value resolves to the updated row → modal re-renders with fresh data, no close-and-reopen needed.

- **Unicode minus-sign regex gotcha.** When asserting on text that includes a minus sign (e.g., negative amounts in refund history like `−₹400.00`), the naive character class `[−-]` is an **invalid regex range** because `−` (U+2212 MINUS SIGN) comes AFTER `-` (U+002D HYPHEN-MINUS) in codepoint order. **Fix**: put the literal `-` first (a leading `-` in a character class is always literal, never a range start): `[-–—−]`. `formatCurrency()` prepends U+2212 (not the ASCII `-`).

- **Label-inversion tests need both present-and-absent assertions.** When testing UI changes that flip semantics (Sales↔Purchases label inversions, REFUND-direction color flips), assert **both** that the new label IS rendered AND that the old/inverted label is NOT. The dual assertion is what catches incomplete clones at the test layer.

- **Parameterised role tests via `describe.each(ROLE_MATRIX)`.** Every role-gated server action needs a parameterised role-access test covering all four roles in a single `describe.each` block. **The DB-call assertion is the critical check** — without `expect(prisma.X.create).not.toHaveBeenCalled()`, a silent guard bypass (action proceeds past `requireRole` somehow) would pass the test. Mock setup: `vi.mocked(requireRole).mockResolvedValueOnce(sessionFor(role))` for allow; `vi.mocked(requireRole).mockRejectedValueOnce(new Error("Forbidden"))` for deny.

- **`prisma.$transaction` in the shared Prisma mock.** The shared Prisma deep mock at `src/lib/__mocks__/prisma.ts` provides a default `$transaction(cb)` implementation that invokes the callback with the same deep-mocked client. Tests for actions wrapped in `prisma.$transaction(async (tx) => …)` work without per-test setup. **When to override**: tests that need to assert rollback behaviour use `vi.mocked(prisma.<model>.<op>).mockRejectedValueOnce(...)`.

- **Chain-ordering test pattern.** When a server-action chain has multiple ordered calls (e.g., attachment replace: `softDeleteAttachment` → `prepareUpload` → R2 PUT → `confirmUpload` → `attach*ToEntity`), individual call-count assertions catch presence but miss order. Use a `callOrder: string[]` accumulator in the file's scope, push the call name from inside each mock's `mockImplementation`, then assert `expect(callOrder).toEqual([...exactSequence])` at the end. Canonical example: `attachment-action-modal.test.tsx`'s `replace flow chain` describe block.

- **`userEvent.upload` bypass for testing client-side MIME rejection.** `<input type="file" accept="image/png,...">` paired with `userEvent.upload` respects the `accept=` filter and **silently drops** disallowed files. To test the JS-side rejection logic, use `fireEvent.change(fileInput, { target: { files: [makeFile("doc.txt", "text/plain")] } })` to assign files directly, bypassing the picker's filter.

- **`useFieldArray` React-key correctness.** When refactoring or testing a `useFieldArray`-based form, **always use `field.id`** as the React `key`, NEVER the array index. Using `idx` as `key` produces silent data swaps when a middle row is removed.

- **Radix Dialog + outside-click in Playwright.** Radix Dialog interprets `page.locator("body").click()` as an outside-pointer event and closes the dialog. **Fix**: blur via `page.keyboard.press("Tab")` inside the dialog — keyboard events don't fire the outside-pointer handler.

- **Playwright walkthrough discipline.** Don't gate on intermediate UI states (a modal closing during transition). React state updates + `router.refresh()` are async and don't expose deterministic intermediate markers on prod latency. Instead, **wait for the final observable assertion** — e.g., the status chip flipping to "Partial" — and let everything in between just happen. Add diagnostic capture (screenshot + form-input count + dialog text snippet) inside a `try`/`catch` around the long-wait `waitForFunction` so a future timeout produces actionable output.

- **Conditional render via `useIsMobile` over CSS-only dual-render.** ResponsiveTable and ResponsiveDialog use a `useIsMobile` hook to render exactly ONE branch (desktop OR mobile) rather than rendering both with CSS `display: none`. **Why not dual-render**: jsdom doesn't apply CSS layout, so `getByText` on row data would match both the hidden desktop table AND the mobile cards. The `useIsMobile` SSR default of `false` (desktop) is deliberate.

- **Window.matchMedia stub in `vitest.setup.ts`.** jsdom doesn't implement `window.matchMedia`. The `useIsMobile` hook calls it on mount and would throw without the stub. Tests that exercise the mobile branch override `window.matchMedia` in a `beforeEach` via `mockMobileViewport()` from `src/test-utils/viewport.ts`.

- **Mobile responsive verification requires actual viewport-level visual checks.** Unit tests with `mockMobileViewport()` verify branch logic and regression-check responsive class strings (`md:contents`, `hidden md:grid`, `h-11 md:h-10`). They do NOT verify visual correctness — JSDOM doesn't evaluate CSS media queries or compute layout boxes. **Pattern**: walkthrough on real phone OR DevTools at 380–390px width BEFORE claiming a phase is mobile-ready.

- **`src/test-utils/viewport.ts` helper for mobile-viewport tests.** Import `mockMobileViewport()` or `mockDesktopViewport()` and call inside `beforeEach` of a `describe('mobile viewport', …)` block. Use a separate `describe` block per mobile-mode test rather than mixing modes — the global stub is reset between test files but not between tests within a file.

### Mirror scripts / entity cloning

- **Underscore-prefixed scratch scripts (`scripts/_*.mjs`) are gitignored by convention.** One-off operational tools (env-var sync, CORS provisioning, prod DB cleanup, file mirroring, etc.) often embed file paths to `.env*.local` or perform admin-scope operations. They MUST NOT be committed. The walkthrough scripts (`scripts/walkthrough-*.mjs`) are committable — they're reusable verification tools that load creds from gitignored env files at runtime.

- **Entity mirroring discipline (casting ↔ plating).** When two entity types share a structural mirror, use the canonical mirror scripts `scripts/_mirror-casting-*-to-plating.mjs` (gitignored). Always:
  - **(a)** Protect shared identifiers from substitution. The current protect list includes `castingPlatingVendor` (camelCase Prisma property — was a Phase 9 leak when missing).
  - **(b)** Run `tsc --noEmit` after every mirror — TypeScript catches camelCase property leaks and shape mismatches that grep won't.
  - **(c)** Grep for unexpected `casting` / `Casting` tokens in the mirrored side.
  - **(d)** Re-apply any type-narrowing casts the mirror obliterates.

- **Mirror script defense-in-depth (consolidated lesson).** Three-layer defense against entity-mirroring bugs:
  - **Layer 1 — `tsc --noEmit`** catches type-level leaks (camelCase Prisma property mismatches, missing types, broken imports).
  - **Layer 2 — Build-time grep** for source-entity string literals in target files. Catches semantic-but-typed-correctly leaks where TypeScript accepts the string because it's a legal discriminated-union member. The Phase 10.5 incident (`entityType="sale"` in `purchases-table.tsx`, attached 4 orphan SALE-typed bills to purchase IDs) was caught only at walkthrough time before this layer existed.
  - **Layer 3 — Unit-level regression guards** in the target entity's table test pin the exact `entityType` value AND the FK-prop contract.

  **All three layers required.** Each catches a different bug class.

- **`ENTITY_MATRIX` pattern for shared-component tests.** Tests for components that ship across entity types (action modals, status chips, transaction-status helpers) use `describe.each(ENTITY_MATRIX)`. Adding a new entity type to the component requires only an array addition.

### Domain / data conventions

- **R2 (Cloudflare) bucket CORS must be set once via S3 API + Admin-scope token.** Browser → R2 PUT via presigned URL silently fails the CORS preflight if the bucket has no CORS policy. **Resolution path**: generate a Cloudflare R2 API token with **Admin Read & Write** scope, apply CORS rules via `@aws-sdk/client-s3`'s `PutBucketCorsCommand`, then revert the prod env to an Object R&W token. CORS rules persist independent of the token that set them — one-time setup.

- **Decimal × BigInt arithmetic via `computeLineTotal`.** Pattern lives in `src/lib/weight-helpers.ts`. Any feature that multiplies a weight by a rate MUST use this helper — **never inline `weightKg.mul(ratePerKg.toString())` anywhere else.** Rounding is `ROUND_HALF_EVEN` (banker's rounding). Companion serialisation rule: `weightKg` columns serialise as **strings** (e.g., `"2.500"`) at the action boundary. Use `formatKg(s)` for display. Never `Number(decimal)` before display arithmetic.

- **Adding `jobType` to `PieceEntry` later (Phase 18 / 18.1 follow-up).** The piece-entry model is intentionally flat — one row per `(employee, day)` with a free-text `note` instead of a structured job type. **Phase 18.1 added `note` to the bulk form**, which absorbs most of the "what job was this?" question for the workshop scale. If the workshop ever needs **structured** job categorisation (e.g., for per-job-type analytics), the extension shape: (1) migration adds `jobType String?` to `piece_entries` (nullable); (2) bulk-piece-entry-section.tsx adds a `jobType` picker per row; (3) rate stays per-row dynamic (no per-job default — the Phase 18.1 lesson was that defaults that are usually overridden are anti-features); (4) `getOutstandingWages` doesn't need to change because wage aggregation is still per-employee. **Don't add `jobType` proactively** — it's purely additive when the need arises, and the existing `note` field probably suffices at workshop scale.

- **FK-vs-discriminator attachment patterns.** Two entity categories handle attachment differently. **(a) Sales/Purchases use discriminator-only**: `attachments.attachedToType` + `attachedToId` is the only link; no FK column on the entity row. Lookup goes through `getAttachmentForEntity(attachedToType, attachedToId)`. The 1:1 invariant is enforced at the application layer via the replace flow. **(b) Casting/Plating use FK + discriminator**: the entry row carries an `attachmentId @unique` column AND `attachments.attachedToType` + `attachedToId` is set. Lookup can go either direction. The `AttachmentActionModal` handles both via optional `onAttach` / `onDetach` props. **Adding a new entity type with attachment support** — choose category based on whether you want the DB to be the source of truth on cardinality.
