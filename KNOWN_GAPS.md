# Known Gaps and Deferred Items

Living document of decisions deferred, caveats accepted, and items to revisit. Audited every 3–4 phases.

## How to use this file

- Items added when a phase intentionally defers work
- Each item has a clear revisit trigger (next phase / next major bump / when condition X happens)
- When an item is resolved, mark it `[resolved on YYYY-MM-DD]` and leave it in place for one audit cycle, then remove

## Decision lineage

Decisions where we deviated from an original spec or assumption, kept for institutional memory.

- **shadcn preset is `radix-nova`, not "default + slate".** The setup spec specified shadcn's classic "Default style + Slate base color." The shadcn CLI (≥4.x) replaced `--style` and `--base-color` with a preset list (Nova / Vega / Maia / Lyra / Mira / Luma / Sera / Custom); none are named "slate." We ran `shadcn init -b radix --css-variables -y` and got the `radix-nova` preset. The visual tokens it shipped are fully overridden in `src/app/globals.css`, so the preset choice is cosmetic-only — but any future `npx shadcn add <component>` will pull components written for the radix-nova variant.

- **Tailwind v4 with CSS-based `@theme`, not `tailwind.config.ts`.** The setup spec said "update `tailwind.config.ts`," but `create-next-app` now scaffolds Tailwind v4, which puts theme tokens in `globals.css` via the `@theme` directive. No `tailwind.config.ts` file exists. End result is the same — design tokens compile to Tailwind utilities and CSS variables.

- **Prisma 7 architecture: schema has no datasource URLs; connection split between `prisma.config.ts` (CLI/migrations) and an adapter on `PrismaClient` (runtime).** The Phase 1.5 spec assumed Prisma 6's pattern of `url = env("DATABASE_URL")` and `directUrl = env("DIRECT_URL")` inside `schema.prisma`. Prisma 7 (installed v7.8.0) rejects both fields in the schema (error P1012). The new architecture: (a) `prisma.config.ts` declares `datasource.url = process.env.DIRECT_URL` for the CLI / migrations / studio (session pooler, port 5432, supports prepared statements); (b) `src/lib/prisma.ts` constructs a `@prisma/adapter-pg` adapter with `process.env.DATABASE_URL` (transaction pooler, port 6543 + `?pgbouncer=true&connection_limit=1`) and passes it to `new PrismaClient({ adapter })` for runtime queries. The two-URL pattern is preserved — just plumbed through two different files instead of one schema block. Adapter dependencies added: `@prisma/adapter-pg`, `pg`, `@types/pg`.

- **Prisma 7 client barrel.** Prisma 7's `prisma-client` generator emits the client into `src/generated/prisma/` as separate files (`client.ts`, `models.ts`, `enums.ts`, etc.) with no `index.ts`. To make `import { PrismaClient } from '@/generated/prisma'` resolve canonically (the idiom that tutorials and AI assistants assume), `scripts/post-prisma-generate.mjs` writes a barrel that re-exports from `./client`. The `prisma:generate` npm script chains generation + barrel; `postinstall` delegates to it so fresh clones always have a working barrel.

- **Tailwind v4 spacing namespace collision — named `--spacing-*` tokens NOT exposed via `@theme`.** DESIGN.md defines spacing as `xs/sm/md/lg/xl = 4/8/16/24/40px`, but Tailwind v4's size-keyword utilities (`max-w-md`, `max-w-lg`, `max-h-xl`, `min-w-sm`, etc.) read from the same `--spacing-*` CSS variable namespace. Defining `--spacing-md: 16px` in `@theme` would shadow Tailwind's default size-keyword resolution and make `max-w-md` = 16px instead of 28rem. Discovered during Phase 1.6 Task 5 when the login card rendered ~200px wide instead of ~450px. Resolution: we use Tailwind's **numeric** spacing utilities exclusively (`p-1` = 4px, `p-2` = 8px, `p-4` = 16px, `p-6` = 24px, `p-10` = 40px) — these derive from the singular `--spacing` base unit (`0.25rem`) and don't collide. Equivalents table is documented in `src/app/globals.css`.

- **Auth.js v5 module augmentation requires `@auth/core/*` paths, not just `next-auth/*`.** Auth.js v5's docs show augmenting `next-auth` and `next-auth/jwt` to add custom fields (e.g. `Session.user.role`, `JWT.role`). In beta.31 reality, the `next-auth/jwt.d.ts` file is `export * from "@auth/core/jwt"` — TypeScript interface merging doesn't propagate through the `export *` re-export. Augmentation must target both the wrapper paths (`next-auth`, `next-auth/jwt`) AND the originals (`@auth/core/types`, `@auth/core/jwt`). See `src/types/next-auth.d.ts` for the four-module declaration. Discovered Phase 1.6 Task 3 — initial spec-shaped augmentation produced TS2322 errors (`token.id` typed as `unknown`).

- **Next.js 16 middleware → proxy rename.** The original Phase 1.6 spec called for `src/middleware.ts`; Next.js 16 deprecated that convention in favor of `src/proxy.ts`. File contents are unchanged (the `auth((req) => …)` wrapper from Auth.js works identically). Critically, **`proxy.ts` defaults to the Node.js runtime** per the official docs, which solves the Auth.js + Prisma edge-bundling problem (the proxy import chain pulls in `@prisma/adapter-pg` → `pg` → `node:net` etc.) without needing to split auth config into `auth.config.ts` + `auth.ts`. Future contributors looking at Auth.js v5 docs will see the split-config pattern; **ignore it** — our stack doesn't need it. Discovered Phase 1.6 Task 4 when the dev server failed to compile middleware.ts under Edge Runtime.

- **Public schema grants revoked from `anon` and `authenticated` roles.** Supabase's default setup grants table-level privileges on `public` to the `anon` (browser-exposed via `NEXT_PUBLIC_SUPABASE_ANON_KEY`) and `authenticated` roles. We don't use Supabase's REST/PostgREST endpoint at all — Prisma talks directly to Postgres through the pooler with the `postgres` role. So those grants were pure attack surface with zero benefit. Phase 1.5 ran:
  ```sql
  REVOKE ALL ON SCHEMA public FROM anon, authenticated;
  REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon, authenticated;
  REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM anon, authenticated;
  REVOKE ALL ON ALL FUNCTIONS IN SCHEMA public FROM anon, authenticated;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON TABLES   FROM anon, authenticated;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON SEQUENCES FROM anon, authenticated;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON FUNCTIONS FROM anon, authenticated;
  ```
  Verified via `has_table_privilege('anon', …, 'SELECT' | 'INSERT')` returning `false` for every check. **If we later want to use Supabase REST for any reason** (Supabase Auth client-side, Realtime, Storage public buckets, etc.), grants need to be re-applied per-table with appropriate RLS policies. Don't blindly `GRANT ALL`.

- **Master data parties (Customers / Suppliers) are for regulars only — walk-in / one-time parties NOT represented in master tables.** Forcing every sale/purchase party through a master record creates friction that doesn't match jewelry-workshop reality. The dual-path party model lands in Phase 3 (Sales) and Phase 4 (Purchases): each Sale/Purchase row gets either `customerId` (FK to a known regular) OR a free-text `partyName` + `partyPhone` pair (one-time / walk-in). The Customers page therefore intentionally has no Excel-bulk-import yet; regulars are entered manually as they emerge. Discovered Phase 2.1 planning. Cross-references: Phase 3 / Phase 4 implement the autocomplete + free-text fallback.

- **Schema extraction pattern for forms with Server Actions.** Zod schemas cannot be exported from files carrying the `'use server'` directive — Next.js compiles non-function exports into client-reference stubs, replacing the actual schema with a serialized handle. When the client form modal imports the "schema," it receives a stub that fails the `zodResolver`'s `isZod4Schema` check (`'_zod' in schema`) at module load with **"Invalid input: not a Zod schema."** Convention going forward: each entity gets a `schema.ts` (no directive — pure validation), `actions.ts` (`'use server'`, imports schema), and form modal (`'use client'`, imports schema). **Same rule applies to type-only exports:** Phase 2.3 originally put `export type { EmployeeForClient }` inside `actions.ts` — Next.js's actions loader can't handle that either, producing a runtime `ReferenceError: EmployeeForClient is not defined` when the form modal imported it. Fix: move shared client-facing types (along with any serializer helpers like `serializeEmployee`) into a separate non-server module (`types.ts`). Pattern committed for Customer in Phase 2.1; Suppliers (Phase 2.2) and Employees (Phase 2.3) follow the same layout — Employees additionally has `types.ts` for `EmployeeForClient` + `serializeEmployee`. Cross-reference Sales (Phase 3) and Purchases (Phase 4) when those land. Discovered Phase 2.1 Task 7; type-export trap discovered Phase 2.3.

- **Prisma enum value imports pull the entire Prisma client runtime into the client bundle.** Phase 2.3 originally had `import { EmployeeType } from "@/generated/prisma"` (value import) at the top of `schema.ts` plus a re-export for components. `EmployeeType` is a runtime const object in Prisma 7's client; the value import drags `@prisma/client/runtime/client.mjs` (which uses `node:module`) into every chunk that imports schema.ts. Through schema.ts → form-modal.tsx → page.tsx the Node-only module ended up in the client bundle, and the first GET /employees returned 500 with `Module not found: node:module`. Rule: **never `import { EnumName }` as a value from `@/generated/prisma`** in any module reachable from a client component. Use `import type { EmployeeType } from "@/generated/prisma"` for type-only references (stripped at compile time, zero runtime cost), and `z.enum(["FIXED", "LABOUR"])` with literal strings for runtime validation. Same rule applies to any Prisma runtime construct (`PrismaClient`, `Prisma.XyzScalarFieldEnum`, etc.) reachable across the boundary. Adjacent class of bug to the schema-extraction pattern above — both about "what gets pulled across the server/client boundary by an incidental import." Discovered Phase 2.3 build smoke.

- **BigInt currency fields stay BigInt only at the Prisma boundary — schema validates plain `number`, action converts at the edges.** `Employee.monthlySalary` is `BigInt? @map("monthly_salary")` in Prisma (paise integer math, future-safe for any salary range). The naive shape — a zod `.transform(v => BigInt(Math.round(v * 100)))` directly in the schema — broke client→server saves: the client form's `handleSubmit` produced a BigInt, then passed that BigInt to the server action, which re-ran `safeParse(input)` and rejected the BigInt with `Expected number, received bigint`. The fix is a three-layer pipeline: (a) **schema** validates rupees as `z.number().int().positive().nullish()` — input AND output shapes are both `number | null`, so client send + server re-parse stay aligned; (b) **action** has a local `toPrismaData()` / `buildSaleData()` helper that converts rupees → `BigInt(Math.round(value * 100))` paise at the Prisma boundary only; (c) **action return** runs a `serializeEntity()` helper from `types.ts` / `sale-helpers.ts` that converts the Prisma row's BigInt back to `number` for JSON safety, returning `EntityForClient` instead of the raw row. JSON cannot encode BigInt; React Server Components' Flight serializer cannot either. **General rule for any future BigInt column**: keep the wire format JSON-safe at both client/server crossings; do the BigInt conversion exactly at the Prisma write and undo it exactly at the action's return. Discovered Phase 2.3 build (Playwright smoke caught the wire-format mismatch). **Extended Phase 3.1** to the Sale entity — three BigInt columns per row (`rate`, `discount`, `total`) all flow through the same pipeline: schema keeps them as `z.number().nonnegative()`, `buildSaleData()` does the BigInt conversion *and* computes the stored total in BigInt math, `serializeSale()` returns `Number` to the client. Every subsequent monetary field in Phase 3.2+ / Phase 4 / Phase 6 follows the same shape.

- **Dual-path party model on `Sale` — denormalized snapshot + nullable FK.** The Sale row has three party-related columns: `customerId` (FK to `Customer`, nullable, `onDelete: SetNull`), `partyName` (required string), and `partyPhone` (optional string). Three operating modes: (1) **linked customer** — `customerId` is set and `partyName`/`partyPhone` are *server-side snapshots* of `Customer.name` / `Customer.phone` at sale time. The form may pass values for these fields, but the action's `buildSaleData()` overwrites them by re-reading the customer row (server is source of truth for FK-linked party data); (2) **walk-in** — `customerId` is null and the two strings are the only identity; (3) **defensive** — if a customer is ever hard-deleted (currently only soft-delete exists, but the FK behavior should survive future schema changes), `onDelete: SetNull` zeroes the FK while leaving `partyName`/`partyPhone` intact, so sale history is preserved. Snapshot pattern is what lets a customer rename (e.g. typo fix) without retroactively rewriting historical sale displays — the row carries the name as-of-the-sale. Discovered Phase 3.1 planning; matches the "regulars only" Phase 2.1 reframe — see the earlier "Master data parties" entry.

- **`Sale.total` is stored at write time, not derived on read.** Computed in the action's `buildSaleData()` helper as `BigInt(qty) × ratePaise − discountPaise` and persisted as a BigInt paise column. Alternative — compute on read — would be simpler at the action layer but loses audit history: if the discount/total logic ever changes (e.g. rounding rules, future per-line-item structure), historical sales would silently shift to the new formula. Stored totals also enable straightforward `SUM(total)` aggregations for dashboards / reports without expression complexity. Trade-off: total must be recomputed on every `updateSale`, and the discount-exceeds-line-total guard fires at the action layer (not the schema) because the formula needs the parsed numbers in scope. Acceptable for ~100 sales/month. Status remains derived (see CLAUDE.md §5) — different concern: status reflects payment/return state which DOES change over time, total reflects the original transaction terms which shouldn't. Discovered Phase 3.1 planning.

- **Per-payment audit trail via `SalePayment` child table — aggregation over column.** Phase 3.2 stores each payment as a separate row in `sale_payments` with `saleId` FK (`onDelete: Cascade`), `amount` BigInt paise, and the standard soft-delete column. `paidAmount` per sale is derived live via `SUM(SalePayment.amount WHERE deletedAt IS NULL)`, never cached on `Sale`. **Rejected alternative**: cached `paidAmount` column on `Sale` updated via trigger or action — adds drift risk (action forgets to update on a path; trigger gets bypassed by raw SQL fix-ups) for negligible aggregation cost at the scale we're at (~100 sales/month × handful of payments each = ~300 SUMs per page render, easily under 10ms with the `@@index([saleId])`). Per-row history is essential for the business — "when did the customer last pay you, and how much?" is the core question this entity exists to answer. Status derives via the same shape — `computeSaleStatus` reads `paidAmount` aggregation + (future) `returnTotal` aggregation, never a stored status field. Discovered Phase 3.2 planning.

- **Overpayment blocked at the action layer, NOT the schema.** Payments exceeding `total − paidAmount` are rejected by `createSalePayment` with `{ ok: false, errors: { amount: ["Exceeds remaining balance. Outstanding: ₹X"] } }` — the formatted outstanding helps the user identify what would have been accepted. **Why action and not schema**: the constraint needs the parsed `amount` + the sale's `total` + the current sum-of-payments in scope; the schema doesn't query the DB. **Why block at all** (vs. allowing overpayment with refund_due status): in practice, overpayment is either (a) a data entry error — catch it immediately and force the user to confirm intent; or (b) the customer paid extra and a refund is owed — which is a return-driven flow handled in Phase 3.3 via `SaleReturn`. Conflating "overpaid by mistake" with "customer overpaid intentionally" would lose the distinction. **`refund_due` status is reserved for return-driven refunds, never payment-driven overpayment.** Cross-reference: Phase 3.3 will add `SaleReturn` and `returnTotal` aggregation; `refund_due` activates there. Discovered Phase 3.2 planning.

- **Payments are immutable — soft-delete + create new, no update.** No `updateSalePayment` action exists. To correct a wrong payment: soft-delete the bad entry (sets `deletedAt`; row stays in the table but is filtered out of `paidAmount` aggregation via `WHERE deletedAt IS NULL`) and create a new correct payment. Both events stay in the history list visible in the detail modal's payment panel. **Why**: preserves audit trail (you can see "wrong ₹500 entry was reversed, replaced with ₹450") — important when reconciling with the customer's own records. **Trade-off**: slightly more UI work for corrections; the user clicks × on the bad row and creates a new one rather than editing in place. The Phase 3.2 inline panel makes this two-click flow ergonomic — × → Confirm reverse → form already expanded with "Pay full balance" ready. Discovered Phase 3.2 planning.

- **Live-updating modal pattern — derive viewed entity from id + parent data, not local snapshot.** When a detail modal shows data that can change via inner UI actions (Phase 3.2: payments; Phase 3.3: returns; Phase 3.4: receipts; future status/balance changes), holding the entity as `useState<EntityForClient>(viewing)` makes the modal show **stale** data after `router.refresh()` — the parent re-fetches, but the modal's local state still references the pre-mutation object. **Canonical fix**: `useState<string | null>(viewingId)` + derive via `parentDataArray.find(x => x.id === viewingId) ?? null`. After mutations call `router.refresh()`, the parent re-fetches → the derived value automatically resolves to the *updated* row → modal re-renders with fresh status / paidAmount / payments / chip in title — all without close-and-reopen. See `sales-table.tsx` Phase 3.2 implementation as the canonical example. **Use this pattern for Phase 3.3's return panel and Phase 3.4's receipt panel**, plus any future inline-edit-in-detail flows. The Phase 3.1 `viewingSale` state worked because nothing inside that modal mutated it; Phase 3.2's payment-panel broke that invariant, so the pattern needed to change. Discovered Phase 3.2 build (Playwright walkthrough's Step 5 critical assertion would have caught the bug if I hadn't fixed it preemptively).

- **RHF triple-generic pattern for transform-emitting schemas.** When a zod schema uses `.transform(...)` (as ours does to coerce `""` → `null` on optional fields), the input and output types differ — `phone: string | null | undefined` going in, `phone: string | null` coming out. RHF v7's `useForm<TFieldValues>` defaults `TTransformedValues = TFieldValues`, which mismatches the resolver's actual return shape. The fix is the **explicit triple generic**: `useForm<FormInput, unknown, FormOutput>` where `FormInput = z.input<typeof schema>` (form's pre-transform value type, allows `defaultValues: { phone: '' }`) and `FormOutput = z.output<typeof schema>` (post-transform shape passed to `onSubmit`). Without it, TypeScript rejects both `defaultValues` and `handleSubmit`. Committed for the Customer form modal in Phase 2.1 Task 4; same pattern for every form modal going forward.

- **Optional-field edit semantics — empty form field means NULL, not "preserve old value."** Customer/Supplier/Employee input schemas use a `.nullish().transform((v) => (v === undefined || v === null || v === "" ? null : v))` pattern (with `.pipe(z.union([z.null(), z.string().email(...)]))` for email so format validation runs after the empty-string normalization). This emits `null` for cleared inputs. Prisma's `update.data` treats `undefined` as "skip this field" but `null` as "set column to NULL" — so emitting `null` makes clearing-via-edit-form actually clear the DB column, not silently retain the stale value. The previous `.transform(() => undefined)` pattern from the Phase 2.1 spec example had this bug. Output type for each optional field is `string | null`, never `string | undefined`. Discovered Phase 2.1 Task 3.

- **Test infrastructure: Vitest + mocked Prisma, no real DB.** All Phase 2.2.5 tests run against `vitest-mock-extended`'s deep-mocked PrismaClient (`src/lib/__mocks__/prisma.ts`); real-DB integration tests are deferred to Phase 8 polish. Component tests use `@testing-library/react` + `user-event` with mocked `next/navigation` and mocked server actions. **Mock at the closest meaningful boundary**: `vi.mock("@/lib/auth-guards", ...)` rather than `vi.mock("@/lib/auth", ...)` — smaller surface, single export, no Auth.js factory coupling. The schema/action/component category split + the canonical mock patterns are documented in `docs/TESTING.md`.

- **Three pre-test extractions to canonical helpers (Phase 2.2.5 Tasks 2–4).** Before tests were written, three patterns were extracted from the duplicated Customer/Supplier code so tests would validate the canonical code, not the duplication: (a) `requireSession()` → `src/lib/auth-guards.ts` (was inlined in two actions.ts files); (b) `<Field>` → `<LabeledField>` in `src/components/labeled-field.tsx` (was duplicated as ~25-line subcomponent in two detail modals); (c) form-control styling → `<FormLabel>` / `<FormInput>` / `<FormTextarea>` / `<FormError>` in `src/components/form-controls.tsx` (was four exported `FIELD_*` className constants per form modal, ~20 lines each). Net change: -32 LOC project-wide; each entity's form-modal dropped from 240 to 191 LOC.

- **Test mock reset conventions split by test category.** Action tests reset Prisma at module scope (`beforeEach(mockReset(prisma))` in `src/lib/__mocks__/prisma.ts`) and reset `requireSession` / `revalidatePath` at file scope. Component tests reset all mocks inside the `describe` block via `beforeEach(vi.clearAllMocks)`. Different mock surfaces (deep-mock vs shallow `vi.fn()`s), different reset semantics; both correct for their case. Don't mix the two reset approaches within one file. See `docs/TESTING.md` for the table.

- **`SaleReturn` as a separate child table, not negative-direction `SalePayment` entries.** Returns are conceptually distinct from payments: one represents "product back," the other "money flow." Mixing them in `SalePayment` would have required type-discrimination on every query and lost the audit-category distinction — "show all returns this month" would become a filter-then-aggregate instead of a direct query. Separate `sale_returns` table preserves the categorical split and keeps two clean per-sale aggregations: `returnTotal = SUM(SaleReturn.refundAmount)` (product side, value-out) vs. `paidAmount = SUM(SalePayment.amount WHERE type=PAYMENT) − SUM(... type=REFUND)` (money side, net). Pattern matches Phase 3.2's `SalePayment`-as-child-table reasoning — aggregate-on-read beats cached columns for the workshop-scale workload. Discovered Phase 3.3 planning.

- **Refunds as `REFUND`-type `SalePayment` entries, NOT a separate `SaleRefund` table.** A refund IS a payment in the opposite direction. Same form (date + amount + note), same workflow (record event + soft-delete + recreate for corrections), same audit history. Adding a `type` enum (`PaymentType { PAYMENT, REFUND }`) on `SalePayment` keeps the payment ledger unified — users always see "Customer paid ₹2,400 on Mar 1, refunded ₹400 on Mar 5" as a single chronological stream. Net `paidAmount = SUM(PAYMENT.amount) − SUM(REFUND.amount)`, both filtered for non-deleted. **Rejected alternative**: a parallel `sale_refunds` table that fragmented the payment history into two streams users would always want to view interleaved. The Phase 3.3 migration adds the `type` column with `@default(PAYMENT)` so existing Phase 3.2 rows backfill correctly (verified via Supabase MCP: 3 pre-existing rows all backfilled to `PAYMENT`, 0 `NULL`, 0 `REFUND`). Single table + discriminator is cleaner. **Note**: this differs from `SaleReturn` (separate table) because Returns and Payments are categorically different concerns, while Payments and Refunds are the same concern in opposite directions. Discovered Phase 3.3 planning.

- **`refund_due` fires on `paidAmount > effectiveTotal` (where `effectiveTotal = total − returnTotal`).** Clean semantic: "the customer has paid more than the now-reduced amount owed." This is the only condition that triggers `refund_due` — pre-Phase-3.3 placeholder logic in `computeSaleStatus` triggered on `balance < 0` which was conceptually the same thing but worded around payments, not returns. The Phase 3.3 rewrite makes the return-driven causation explicit. **Edge case**: full return with no payment (`returnTotal === sale.total, paidAmount === 0n`) resolves to `completed` (sale is closed, nothing was ever owed back) — the `returnTotal > 0n` guard distinguishes "fully returned" from "degenerate ₹0 sale" (which stays `pending`). The full-return-no-payment case is unreachable in production because `createSaleReturn` validates cumulative `refundAmount ≤ sale.total`, but the function handles it gracefully for direct-API safety. Discovered Phase 3.3 planning; tested across 16 sale-status boundary cases.

- **Returns are immutable — soft-delete + create new (same as payments).** No `updateSaleReturn` action exists. Wrong return → soft-delete the bad entry (sets `deletedAt`; row stays but is filtered out of `returnTotal` aggregation) + create new correct return. Audit trail preserved. **Cross-row status interaction**: soft-deleting a return changes `effectiveTotal` which can flip status in either direction — `refund_due → completed/partial` when undoing a return whose refund hadn't been issued yet, `completed → partial` when undoing a return that had reduced effectiveTotal to match paidAmount, etc. Same applies to soft-deleting a `REFUND`-type `SalePayment` (Phase 3.3 walkthrough Step 12 exercises this: a sale that's `completed` after refund issuance flips back to `refund_due` if the refund payment is soft-deleted while the return remains active). The `viewingSaleId` live-update pattern handles the chip recomputation without modal close-and-reopen. Discovered Phase 3.3 planning.

- **Unified `computeTransactionStatus` helper for Sales + Purchases.** Phase 4 introduced Purchases as a structural mirror of Sales. The status math is identical across both entities (`pending` / `partial` / `completed` / `refund_due` derived from `total`, net `paidAmount`, `returnTotal`) — no entity-specific divergence in thresholds or edge cases. Decision: rename `src/lib/sale-status.ts` → `src/lib/transaction-status.ts`, rename `computeSaleStatus` → `computeTransactionStatus`, keep `SaleStatus` and `PurchaseStatus` as **type aliases** in each entity's helpers (`sales/sale-helpers.ts` re-exports `type SaleStatus = TransactionStatus`; `purchases/purchase-helpers.ts` declares `export type PurchaseStatus = TransactionStatus`) for call-site readability. **Rejected alternative**: a thin `purchase-status.ts` that just re-exports the Sales helper — adds ceremony with no benefit since the math is genuinely shared. **Rejected alternative B**: two parallel implementations — invites silent drift if one is patched without the other. **Trade-off**: tight coupling between Sales and Purchases status logic. **Rationale**: divergence in status rules between sales and purchases is implausible at this scale; if it ever happens, the single file is the obvious extension point with predictable refactor cost. The unified `<TransactionStatusChip>` (in `src/components/`, not in either entity folder) follows the same pattern — single component, both folders import it. Discovered Phase 4 planning.

- **UI label inversions for supplier-direction (Purchases) — same enum, same status, opposite money direction.** Phase 4 introduced semantic inversions where the same `PaymentType` enum + same `refund_due` status mean opposite money-direction depending on which entity owns the row. The mental model that ties it together: **red = money OUT of shop; blue/secondary = money IN to shop, regardless of which entity owns the row.** Concrete inversions wired into `purchases/payment-panel.tsx`:
  - "Outstanding" (Sales: customer owes shop) → "Owed to supplier" (Purchases: shop owes supplier)
  - "Refund owed" (Sales: shop owes customer back) → "Refund expected" (Purchases: supplier owes shop back)
  - Indicator color when refund_due fires: `text-error` (red, Sales) → `text-secondary` (blue, Purchases) — money IN is positive
  - Trigger button label when refund_due fires: "+ Issue refund" (Sales) → "+ Record refund received" (Purchases)
  - REFUND-row label in history: "Refund" (Sales) → "Refund received" (Purchases)
  - REFUND-row text color: `text-error` (Sales) → `text-secondary` (Purchases)
  - REFUND-row amount prefix: `−` (Sales: money out) → `+` (Purchases: money in)
  - Server error message in `payment-actions.ts` overpayment rejection: "Outstanding: ₹X" (Sales) → "Owed to supplier: ₹X" (Purchases)

  The label inversions are the **most visible Sales-vs-Purchases difference** from the user's perspective; the schema clones cleanly, the actions clone cleanly, but copy-paste regressions in the UI would silently leak Sales-direction language into the Purchases panels. The Phase 4 walkthrough's Step 7 + Step 11 explicitly assert on the inverted labels (and the `payment-panel.test.tsx` does dual-assertion: positive on the new label + negative on the old). Discovered Phase 4 planning.

- **Walk-in auto-promotion via phone identity (Phase 6).** When a sale or purchase is saved as walk-in (no explicit `customerId`/`supplierId`) but WITH a populated `partyPhone`, the server transactionally either links to an existing Customer/Supplier (matched by normalized phone) or auto-creates one. Walk-ins without phone stay as snapshot-only entries — no auto-creation since identity cannot be confirmed. The whole flow (`tx.customer.findFirst` → optional `tx.customer.create` → `tx.sale.create`) runs in `prisma.$transaction`, so customer/supplier creation and sale/purchase creation succeed or fail together. **Rationale**: user-stated workflow problem — *"if I enter xyz in sales as walkin it should be updated into the customers same for purchase so that the name does not change if they are same"*. Phone is the most reliable identity proxy at this workflow's scale (~100 transactions/month, small known party list, no GST/PAN identifiers tracked yet). The action *also* re-snapshots `partyName` from the canonical Customer/Supplier row on every save — so the second walk-in with the same phone but a different typed name carries the canonical name, not the new typed string. - **Phone normalization at every boundary (Phase 6).** `normalizePhone(s)` in `src/lib/phone.ts` strips whitespace, dashes, and parens; preserves leading `+` for international format; returns `null` for empty/whitespace-only input. Idempotent — running normalization on already-clean input is a no-op. Applied at **every storage boundary** (`Customer.phone`, `Supplier.phone`, `Sale.partyPhone`, `Purchase.partyPhone` schema transforms) AND at **every lookup boundary** (auto-promotion `findFirst` queries, party-picker phone-prefix matching). Without symmetric normalization, lookups miss already-stored records (typed `9876-543-210` would not match stored `9876543210`). The `+`-preservation is deliberate: international numbers with a leading `+` are kept distinct from the same digits without `+`, so `+919876543210` and `919876543210` would NOT match each other — accepted trade-off, no current Indian-only workflow uses the leading `+`. Discovered Phase 6 planning.

- **Party picker phone-prefix matching (Phase 6).** Typing digits into the party picker now surfaces customers/suppliers whose **normalized phone starts with** the typed prefix, in addition to the existing name-substring match. **Pure-letter queries skip phone matching entirely** (the picker only considers phone candidates when the query contains at least one digit) — avoids spurious hits if a stored phone ever happened to contain letters. Mixed-alphanumeric queries match by name only (the query is treated as a name substring; the picker doesn't try to extract digits from a mixed string). Both the candidate phone and the query digits are run through `normalizePhone` before comparing, so `9876-543-210` stored matches `9876` typed and vice versa. The "Use as walk-in: …" footer entry stays at the bottom regardless of match results. Discovered Phase 6 planning.

A small phase (~3–4h) before adding any 5th user is worth doing. Scope: invite-by-email flow, role-selection dropdown (typed against the four-role enum), password reset trigger, current-password change for the logged-in user. **Revisit before adding a 5th user, or when an admin needs to onboard staff without DB access.** Ties together with the existing "Invite user flow not built" / "No password reset flow" / "Admin password rotation deferred" items — solving this one resolves the trio.

- **Casting and Plating pages not yet built.** Routes `/casting` and `/plating` are gated by the proxy (only `ADMIN` and `CASTING_PLATING_MGMT` can reach them; everyone else redirects to `/dashboard`) and the sidebar shows them as "Soon" badges for those two roles. `CASTING_PLATING_MGMT` users currently see only their dashboard placeholder card. **Revisit in Phase 9** (casting + plating tracking, ~5–6h estimate). Phase 9 depends on Phase 8 (bill upload infrastructure). When the pages land, also drop the `enabled: false` flags on the two sidebar items in `src/app/(app)/sidebar.tsx` and remove the dashboard placeholder.

- **No staging / preview environment.** Prod is fed directly from `main`. There is no `staging` branch with a preview URL, no PR-preview deployments, no canary releases. Every push to `main` becomes production within ~60s. **Acceptable for current single-developer mode**; revisit if a second developer joins or if the change rate produces enough regressions to justify a gate. Vercel's Rolling Releases feature is the natural extension when needed.

- **No custom domain.** App is served from `jewlerytracker-darshan-somaiyas-projects.vercel.app`. **Revisit when ready to bind something like `app.shreecreation.com`.** Custom domains also bypass Vercel SSO Protection by default, so binding a domain is the cleanest path if you ever want to re-enable SSO for the `*.vercel.app` URL without locking yourself out. (SSO is currently OFF for this project since the app has its own Auth.js.)

- **No app-side backup automation.** Supabase Free tier provides daily backups retained 7 days. No custom `pg_dump` schedule, no off-cloud copy, no point-in-time recovery (a paid Supabase tier feature). For ~100 transactions/month this is probably fine — but if a destructive bug ships and isn't noticed for >7 days, recovery is impossible. **Revisit if data volume or operational risk grows.** Implementation when needed: a GitHub Action that runs `pg_dump` against `DIRECT_URL` weekly and uploads to a private bucket / repo asset.

- **No third-party observability** (Sentry, Datadog, Logtail, etc.). The only custom logging is the `console.error` in `src/lib/auth.ts`'s authorize wrapper. Vercel's built-in runtime logs are available but ephemeral (no long-term retention on free tier) and not queryable beyond keyword filter. **Revisit when a real prod error needs deep investigation** and the Vercel log retention proves insufficient. Sentry's Vercel integration is one-click for app errors; for DB / Prisma instrumentation Datadog's Vercel marketplace integration is the typical pick.

- **No CI / pre-deploy quality gate.** A push to `main` deploys without first running `npm run test:run` or `npx tsc --noEmit` in CI. A test-failing or type-broken commit will deploy if it survives the Vercel build (which only catches TS errors that block compilation, not Vitest failures). **Revisit when broken-main incidents start happening** — a GitHub Actions workflow that runs tests + typecheck on every push and blocks the Vercel deploy on failure is the standard fix. Cost: ~3 minutes per push, requires adding a CI config and possibly switching to a Vercel "deploy only on CI green" mode. Not urgent at single-developer velocity.

- **The Vercel CLI is not installed locally.** Convenience commands like `vercel logs --follow`, `vercel env pull`, `vercel inspect`, and direct `vercel deploy` from the CLI are unavailable. The Vercel Plugin / MCP tooling fills most of the gap (deployment trigger, runtime logs, build logs). **Install when something the MCP doesn't surface becomes painful** — `npm i -g vercel` is a single command.

- **Hydration warnings on date / datetime fields.** Production navigation logs ~9 instances of React error #418 ("Text content does not match server-rendered HTML") per session. Surfaced during the Phase 6 walkthrough (`scripts/walkthrough-p6-auto-promo.mjs` Browser diagnostics block). Almost certainly a date/timezone formatting mismatch between the server container (UTC) and the client browser (`Asia/Kolkata`) — `formatDate` / `formatDateTime` in `src/lib/format.ts` run on both sides and produce slightly different strings when the system clock crosses a date boundary in IST vs UTC, or when the locale defaults differ between Node and the browser. Doesn't affect functionality (all walkthrough assertions passed), but pollutes the browser console and indicates SSR drift. Diagnostic plan: enable React's non-minified runtime in a preview deploy → identify the offending render → pin timezone explicitly in the formatter on both sides (e.g., `Intl.DateTimeFormat('en-IN', { timeZone: 'Asia/Kolkata', ... })` for the server, matching the client). **Estimated effort: ~30 minutes** once the offending render is identified. Defer to a polish phase. Discovered Phase 6 walkthrough.

## Onboarding notes for future contributors

Things that aren't gaps but trip up new sessions.

- **MCP authentication is per-developer.** `.mcp.json` at project root declares the Supabase MCP server, but OAuth tokens are stored in each developer's local Claude Code state — not in the repo. A new session in this folder must run `claude /mcp` in a regular terminal (outside the IDE), select `supabase`, and complete OAuth before MCP tools work. The `.mcp.json` file itself is committed; tokens are not.

- **Dev server default port may be 3001, not 3000.** If another long-running node process holds port 3000, `next dev` falls back to 3001 with a `⚠ Port 3000 is in use` warning. Check the dev.log / terminal output for the actual port before opening the browser. To free port 3000: `Get-Process node` (Windows) or `lsof -i :3000` (mac/linux) → identify the holder → kill it if it's a stale dev server.

- **Tailwind v4 — theme tokens live in `src/app/globals.css`, NOT in a JS config file.** Don't go looking for `tailwind.config.ts` — it doesn't exist. All color/font/radius tokens are defined in the `@theme { … }` block inside `globals.css`. If you need to add a new color or change a token, edit `globals.css`. The `@theme` directive auto-generates Tailwind utility classes (`bg-surface-container`, `text-on-primary`, etc.) and CSS custom properties (`var(--color-surface)`) from the declarations.

- **Supabase keys use the new `sb_publishable_…` / `sb_secret_…` format**, not legacy JWTs. The env var names in `.env.local` retain the legacy `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY` convention from the original spec, but the values are new-format. `@supabase/supabase-js@2.105+` accepts both formats. Don't be surprised that the values don't look like JWTs.

- **DB password contains URL sub-delim characters** (`,` and `*`). It's URL-encoded as `%2C` and `%2A` inside both `DATABASE_URL` and `DIRECT_URL` so Prisma's URL parser doesn't choke. If you regenerate the password and it contains other reserved characters (`+`, `&`, `?`, `#`, `/`, `@`, `:`, space), URL-encode them too. The raw password roundtrips correctly server-side.

- **Currency is stored as integer paise**, not rupees-with-decimals. `₹1,234.56` ↔ `123456` paise. Never store, sum, or arithmetic-on currency as a float anywhere. **Three-layer pipeline** established in Phase 2.3 (`Employee.monthlySalary` is the first monetary column; Sales / Purchases / FixedSalary / WorkEntry follow the same pattern in Phase 3+):
  1. **Prisma column:** `BigInt? @map("monthly_salary")` — paise integer math, safe for any salary range.
  2. **Schema:** validates rupees as `z.number().int().positive().nullish()` — wire-format identical on client send and server re-parse. **Do NOT** put a `.transform(v => BigInt(...))` in the schema — see KNOWN_GAPS decision lineage for the "wire-format mismatch" reason.
  3. **Action:** a local `toPrismaData()` helper converts rupees → `BigInt(Math.round(value * 100))` paise at the Prisma write only. On return, `serializeEntity()` (in `<entity>/types.ts`) converts BigInt back to `number` for JSON safety. UI receives `EntityForClient` with `monthlyXxx: number | null` and renders via `formatCurrency(paise)` from `src/lib/format.ts`.

- **Server/client module-boundary discipline.** Three classes of bug have surfaced from incidental imports crossing the boundary; all share the same lesson — *what's reachable from a client component must be bundleable for the browser*. Before adding a new entity or import, ask "what does this pull along with it?"
  - **Zod schemas exported from `'use server'` files** are compiled into client-reference stubs by Next.js (Phase 2.1). Keep schemas in `schema.ts` (no directive); actions import the schema.
  - **Type-only exports from `'use server'` files** also break — Next.js's actions loader produces `ReferenceError: TypeName is not defined` at runtime when a client component imports the type (Phase 2.3). Keep client-facing types and serializer helpers in `types.ts`, not in `actions.ts`.
  - **Prisma enum value imports** (e.g. `import { EmployeeType } from "@/generated/prisma"`) pull `@prisma/client/runtime/client.mjs` (which uses `node:module`) into the client bundle (Phase 2.3). Use `import type { EmployeeType }` for type-only references; use `z.enum(["FIXED", "LABOUR"])` with literal strings for runtime validation. Never re-export Prisma's runtime enum values to code that crosses the boundary.

  General principle: if a value (not a type) crosses from server-only territory to client-reachable territory, audit its transitive imports for Node-only modules (`node:*`, `pg`, `fs`, `crypto` outside Web Crypto), Next.js server-action stubs, or anything carrying `'use server'`.

- **Status is derived, not stored.** Don't add a `status` column to `Sale` or `Purchase`. See `CLAUDE.md` §5 for the full rationale and the TypeScript string-literal union pattern.

- **Schema change workflow.** When adding or modifying a Prisma model:
  1. Edit `prisma/schema.prisma`
  2. `npx prisma migrate dev --name <description>` — applies the migration to the DB via `DIRECT_URL`
  3. `npm run prisma:generate` — Prisma 7 doesn't auto-regenerate after `migrate dev`; this also writes the `src/generated/prisma/index.ts` barrel
  4. **Restart the dev server** — `src/lib/prisma.ts` caches the `PrismaClient` instance in `globalThis.prisma` to prevent connection exhaustion under HMR. New models will be `undefined` on the running singleton until the process restarts (`prisma.customer` would throw `Cannot read properties of undefined (reading 'findMany')`). Discovered Phase 2.1 Task 7.

  Fresh clones get steps 3 + 1-via-`migrate deploy` from the `postinstall` hook in `package.json` — but during active development, all four steps are manual.

- **Build-cache cousins — `rm -rf .next/` is the universal first-aid kit when "I changed something and the dev server is still serving stale behavior."** Turbopack's compiled chunks under `.next/` can pin to a build's view of env-dependent module evaluation, CSS token resolution, or generated-client shape. Symptoms seen across phases:
  - **Phase 1.6 Task 5:** Tailwind CSS chunk served stale `--spacing-md` mapping after `globals.css` edits; HMR didn't pick up the change. Fix: `.next/` nuke + cold restart.
  - **Phase 2.1 Task 7:** Prisma client singleton (`globalForPrisma.prisma`) was instantiated before a new model was added; even after dev-server restart, the new model was `undefined`. Fix: `.next/` nuke + cold restart.
  - **Phase 2.1 credential rotation Task B:** Prisma reported `Authentication failed against the database server` after a verified-correct DB password change. Direct `pg` driver test with the same `DATABASE_URL` succeeded; only the dev server's Prisma adapter failed. Fix: `.next/` nuke + cold restart.

  **First diagnostic step** when a change to env vars, `globals.css`, `schema.prisma`, or any generated code doesn't take effect after a normal dev-server restart: stop the dev process, `rm -rf .next/`, restart. Saves hours over speculative debugging. The cost is a one-time recompile (~5 sec).

- **Postgres `anon` and `authenticated` roles have no privileges on the `public` schema.** New tables don't need RLS policies for security (the only roles that can access them are `postgres` / `service_role`, both of which `BYPASSRLS`). Adding RLS as defense-in-depth is fine. If you see "RLS disabled" advisories from Supabase, **the threat is mitigated by the grant revocation** — see decision lineage. Schema-level USAGE remains for the two roles (inherited from the `PUBLIC` role) but is harmless without table grants.

- **Prisma client output lives at `src/generated/prisma/` (gitignored).** The directory is regenerated by `npm run prisma:generate`. Never edit files inside it directly. Importing pattern: `import { prisma } from '@/lib/prisma'` for the singleton; `import { PrismaClient, Prisma, $Enums } from '@/generated/prisma'` for type imports.

- **First-time setup after `git clone`.** Required steps before the dev server is useful: (1) `npm install` (runs `postinstall` → `prisma generate` → barrel write automatically); (2) populate `.env.local` from `.env.example` — values come from Supabase dashboard + a fresh `openssl rand -base64 32` for `AUTH_SECRET` + a chosen `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` (12+ chars); (3) `npx prisma migrate deploy` to apply existing migrations to your DB; (4) `npx prisma db seed` to create the admin user; (5) `npm run dev` to start the server; (6) sign in at `/auth/login` with the seeded credentials. Skipping step 4 means there's no user to log in as.

- **JWT sessions — no DB session table.** Auth.js is configured with `session: { strategy: 'jwt', maxAge: 30 days }`. Sessions are stateless JWE cookies signed/encrypted with `AUTH_SECRET`. There is no `sessions` table in the DB and no `@auth/prisma-adapter` involvement (despite the package being installed — it's available for a future switch but not wired up). To invalidate all sessions globally (e.g. after a security incident), **rotate `AUTH_SECRET` in `.env.local`**. Every existing cookie becomes undecryptable; everyone is forced to re-authenticate.

- **Heading fonts cascade from `@layer base`, not from per-element classes.** All `h1`–`h6` elements automatically use Geist via `html, body { font-family: var(--font-sans); }` + `h1, h2, h3, h4, h5, h6 { font-family: var(--font-display); }` in `src/app/globals.css`. **Don't add `font-display` to heading elements** — it's redundant and creates inconsistent patterns across pages. Only use `font-display` on **non-heading** elements that should look like headings (e.g. the dashboard card's stat number uses `font-display text-2xl font-semibold` on a `<p>` because `<p>` defaults to Inter).

- **Tables with Prisma `@updatedAt` — direct-SQL `UPDATE`s via Supabase MCP must set `"updatedAt" = NOW()` explicitly.** Prisma's `@updatedAt` is application-managed (the Prisma client sets the column on every update call), NOT a DB trigger. All app code goes through Prisma and inherits this automatically — but ad-hoc `UPDATE` statements run through the Supabase MCP `execute_sql` tool (for debugging, manual restores, role flips, etc.) won't touch `updatedAt` unless you include it: `UPDATE users SET role = 'STAFF', "updatedAt" = NOW() WHERE id = '…'`. The column has a NOT NULL constraint, so omitting it on an `UPDATE` will be silent unless you've cleared it, in which case the statement fails.

- **Per-entity folder convention.** Each CRUD entity (Customers built in Phase 2.1; Suppliers, Employees, Sales, Purchases follow) lives under `src/app/(app)/<entity>/` with this fixed layout:
  - `page.tsx` — server component, queries the entity list, embeds the client table
  - `schema.ts` — zod validation, **plain TS, no `'use server'` directive** (see decision lineage for why)
  - `actions.ts` — `'use server'`, imports the schema, exports `create<Entity>` / `update<Entity>` / `softDelete<Entity>`
  - `<entity>-table.tsx` — client component, TanStack Table v8, search + sort + zebra striping + Edit/Delete row actions
  - `<entity>-form-modal.tsx` — client component, RHF + zodResolver with the triple-generic pattern; one component serves both add and edit (mode toggled by `customer` prop)
  - `<entity>-detail-modal.tsx` — client component, read-only view with Edit/Delete footer (Delete shows inline confirmation, no second-modal layer)

  Soft delete is mandatory: every entity that touches business data gets a nullable `deletedAt` column + an index on it. List queries filter `where: { deletedAt: null }`. Restore is via direct DB UPDATE (see deferred items).

- **Running tests.** Three scripts:
  - `npm test` — Vitest watch mode for development (re-runs affected tests on save)
  - `npm run test:run` — one-shot run, used by CI / pre-commit hooks
  - `npm run test:coverage` — one-shot with `@vitest/coverage-v8` baseline (Phase 2.2.5 baseline: ~71% statements project-wide, ~66% for the customers folder, ~87% for `src/components/`; will improve as new test categories land)

  Run a single test file: `npx vitest run path/to/file.test.ts`. Run a single test by name: `npx vitest run -t "rejects empty name"`.

- **Adding a new entity (Phase 2.3 onward).** The per-entity scaffolding convention above now extends to test coverage. Each entity must include: `schema.test.ts` (zod-only, no mocks), `actions.test.ts` (mocked Prisma + auth-guards + next/cache), and a component test on the entity's table (`<entity>-table.test.tsx`). Use the Customer/Supplier files as templates (~24 schema + 11 action + 14 component tests per entity). **Don't extract shared test helpers preemptively** — extraction belongs in a follow-up phase after three entities exist and the right shape is visible.

- **Test count reporting from Phase 2.3 onward.** The "Test count delta" line in every phase report stops being `N/A`. Format: `<previous total> → <new total> (+N net new, M skipped with reason)`. Skipped tests must include a reason (e.g., "skipped: covered by Phase 2.2.5 component test on identical surface"). `N/A` is no longer an acceptable value once tests exist for the layer being modified.

- **Test inputs to actions match `z.output<schema>`, not the raw form input shape.** Unit tests bypass the form layer and call the server action directly. The action's exported parameter type is `z.infer<typeof schema>` which equals `z.output` — the post-coercion shape. So test fixtures must construct values matching the OUTPUT, not the pre-coercion FORM shape. Concrete example from Phase 3.1: `SaleInput.date` is `Date` after `z.coerce.date()`, so `validInput()` must construct `new Date("2026-05-14T00:00:00Z")`, not the form's `"2026-05-14"` string. The schema's coercion path is exercised separately in `schema.test.ts`. **TypeScript catches this at `tsc --noEmit` time**; if you see "Argument of type 'string' is not assignable to parameter of type 'Date'" pointing at a test helper, the fix is the helper, not a cast. (Currency is the inverted case but works the same way: `rate: number` rupees stays a number in the schema output, and the action does the BigInt conversion internally — tests pass rupee numbers, not paise BigInts.)

- **`fireEvent.focus()` for jsdom React onFocus handlers.** Programmatic `element.focus()` in jsdom dispatches a native focus event, but it does NOT reliably trigger React's synthetic `onFocus`/`onBlur`/`onMouseEnter`/etc. handlers. Tests that rely on these handlers firing (e.g., a dropdown that opens on input focus) need explicit React-event dispatch: `import { fireEvent } from '@testing-library/react'` then `fireEvent.focus(input)`. `userEvent.click(input)` also works for the focus case (it dispatches the full mousedown→focus→mouseup→click sequence through React). Discovered Phase 3.1 — five party-picker tests failed because `input.focus()` didn't open the dropdown. Same gotcha applies to any synthetic-only React event handler.

- **Live-updating modal pattern — detail modals that show mutable data must derive, not snapshot.** When a detail modal exposes inner UI that mutates the entity (Phase 3.2 payments; Phase 3.3 returns; Phase 3.4 receipts; future status-changing actions), do NOT hold the entity as `useState<EntityForClient>(viewing)`. After `router.refresh()` the parent re-fetches but the modal's local state still references the *stale* pre-mutation object → status chip stays "Pending", payment list doesn't update, outstanding balance doesn't recompute. **Canonical pattern**: `useState<string | null>(viewingId)` + derive via `const viewing = viewingId ? parentDataArray.find(x => x.id === viewingId) ?? null : null`. After mutations call `router.refresh()`, the parent re-fetches → the derived value resolves to the updated row → modal re-renders with fresh data, no close-and-reopen needed. See `src/app/(app)/sales/sales-table.tsx` for the canonical implementation (`viewingSaleId` + the `sales.find` lookup). **Use this pattern by default** for any future detail-modal pattern where inner UI can mutate the underlying entity. Discovered Phase 3.2.

- **Unicode minus-sign regex gotcha.** When asserting on text that includes a minus sign (e.g., negative amounts in refund history like `−₹400.00`), the naive character class `[−-]` is an **invalid regex range** because `−` (U+2212 MINUS SIGN) comes AFTER `-` (U+002D HYPHEN-MINUS) in codepoint order. JS rejects with `SyntaxError: Invalid regular expression: ... Range out of order in character class`. **Fix**: put the literal `-` first (a leading `-` in a character class is always literal, never a range start): `[-–—−]` matches hyphen-minus, en-dash, em-dash, and math-minus. **Alternative**: explicit Unicode escapes `[-–—−]`. Encountered twice during Phase 3.3 — the Playwright walkthrough script `scripts/walkthrough-returns.mjs` failed with this exact syntax error, then the same trap re-surfaced in `payment-panel.test.tsx`'s assertion on REFUND-row rendering. `formatCurrency()` prepends U+2212 (not the ASCII `-`) via the panel's `amountDisplay` builder, so any test that asserts on negative-amount strings must use the literal-first character class. Onboarding rule: **if you write `[X-Y]` in a character class where X or Y is a Unicode codepoint above U+00FF, double-check the codepoint order and use the leading-`-`-as-literal trick instead.**

- **Label-inversion tests need both present-and-absent assertions.** When testing UI changes that flip semantics — Sales↔Purchases label inversions ("Outstanding" ↔ "Owed to supplier"), REFUND-direction color flips (`text-error` ↔ `text-secondary`), or any future semantic inversion — assert **both** that the new label IS rendered AND that the old/inverted label is NOT. Without the negative assertion, a copy-paste regression that leaves the original Sales-direction label still rendering would silently pass: the test author wrote `getByText(/^Owed to supplier:/i)`, the new label IS present, and the leaked old label sits invisibly alongside it. The dual assertion is what catches incomplete clones at the test layer. Example from `purchases/payment-panel.test.tsx`: `expect(screen.getByText(/owed to supplier:/i)).toBeInTheDocument()` AND `expect(screen.queryByText(/^outstanding:/i)).not.toBeInTheDocument()`. Same pattern for class assertions: `expect(badge).toHaveClass("text-secondary")` AND `expect(badge).not.toHaveClass("text-error")`. **Apply by default for any inversion test** — costs almost nothing, catches the class of regression that's hardest to spot during code review. Discovered Phase 4.

- **Never `source` / `set -a` `.env*` files that contain URL query strings.** Bash treats unescaped `&` as a background-job operator, silently truncating values like `DATABASE_URL=postgresql://...?pgbouncer=true&connection_limit=1` at the first `&` (and possibly storing an empty value if the rest of the line gets parsed as a separate command). The bug is invisible at the script layer — the variable IS set, just to the wrong value. Phase 4.5 hit this exact trap during the initial Vercel env-var upload: stored an empty `DATABASE_URL` in production for ~30 minutes before a debug endpoint surfaced `length: 0`. **Canonical pattern**: parse env files via Node, not via shell. Either `import { config } from 'dotenv'; config({ path: '.env.production.local' })`, or a one-shot `node -e` script that reads the file with `fs.readFileSync` and a regex. The repo's `scripts/walkthrough-prod.mjs` and `scripts/walkthrough-sales.mjs` show the read-with-regex pattern. **Detection trick** when you suspect env-var corruption against Vercel or any platform that encrypts at rest: temporarily expose presence + length (NOT values) via a token-gated debug route — see the (deleted) `src/app/api/debug-env/route.ts` git history for the shape. Discovered Phase 4.5.

- **Lazy Prisma client construction is required by Next.js 16 build-time page-data collection.** `src/lib/prisma.ts` wraps `PrismaClient` in a `Proxy` so connection-string read + adapter construction defer to first property access. **Do NOT** revert to eager construction (`const prisma = new PrismaClient(...)` at module load). Next.js 16 imports route modules during the "Collecting page data" build phase to extract metadata; eager construction would fire a throw on missing `DATABASE_URL` even when the env IS configured for runtime, because the build's env-resolution timing differs from runtime's. The throw still triggers correctly at runtime if the env is actually missing — it just no longer crashes the build. Phase 4.5 fixed this. See `docs/HANDOFF.md` § 3 and the file's header comment for the canonical lazy-client pattern.

- **Breaking enum migrations in non-interactive contexts.** `prisma migrate dev` requires interactive confirmation for breaking enum changes (removing a value, renaming, etc.) — the prompt "Are you sure you want to continue?" is unskippable and `--create-only` doesn't change this. In CI, agent shells, or any non-TTY context, the canonical workaround is: (1) update `prisma/schema.prisma`; (2) generate the SQL via `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script` to stdout; (3) hand-create the migration directory under `prisma/migrations/<timestamp>_<name>/` and paste the SQL into `migration.sql`; (4) apply with `npx prisma migrate deploy`, which is non-interactive and works against any environment. **Canonical example**: Phase 5 migration 2 (`20260515183353_role_remove_staff`) removed the `STAFF` enum value via this exact pattern — Prisma's diff produced the standard CREATE-new-type → ALTER-COLUMN → DROP-old-type sequence, written by hand into the migration file, applied to both dev and production via `migrate deploy`. Discovered Phase 5 migration.

- **Parameterised role tests via `describe.each(ROLE_MATRIX)`.** Every role-gated server action needs a parameterised role-access test that covers all four roles in a single `describe.each` block. The matrix is `[["ADMIN", boolean], ["PURCHASE_DEPT", boolean], ["LABOUR_MGMT", boolean], ["CASTING_PLATING_MGMT", boolean]]` where the boolean is `allowed`. Each case branches: allowed roles assert `result.ok === true` AND `prisma.<table>.<op>` was called once; denied roles assert the action throws `"Forbidden"` AND `prisma.<table>.<op>` was NOT called. **The DB-call assertion is the critical check** — without `expect(prisma.X.create).not.toHaveBeenCalled()`, a silent guard bypass (action proceeds past `requireRole` somehow) would pass the test. Pattern lives in every `*-actions.test.ts` file under the "Phase 5 RBAC" describe block. Mock setup: `vi.mocked(requireRole).mockResolvedValueOnce(sessionFor(role))` for allow; `vi.mocked(requireRole).mockRejectedValueOnce(new Error("Forbidden"))` for deny. Use `mockResolvedValueOnce` (not the default `mockResolvedValue` from `beforeEach`) so the per-test mock doesn't bleed into subsequent tests. Discovered Phase 5 tests.

- **`prisma.$transaction` in the shared Prisma mock.** The shared Prisma deep mock at `src/lib/__mocks__/prisma.ts` provides a default `$transaction(cb)` implementation that invokes the callback with the same deep-mocked client and returns its result. Tests for actions wrapped in `prisma.$transaction(async (tx) => …)` work without per-test setup — the existing `vi.mocked(prisma.<model>.<op>)` configurations fire through the tx path identically to a non-transaction action. **When to override**: tests that need to assert rollback behaviour ("if inner `tx.customer.create` throws, outer `tx.sale.create` is never called") use `vi.mocked(prisma.customer.create).mockRejectedValueOnce(...)` — the default `$transaction` impl propagates the throw and the per-test rejection rolls everything. Per-test `vi.mocked(prisma.$transaction).mockImplementationOnce(...)` is also available for finer control. Discovered Phase 6 build.
