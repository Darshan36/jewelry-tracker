## Decision lineage (Phase 1 through Phase 11)

Foundational decisions kept for institutional memory.

### Phase 1 — Foundation

- **shadcn preset is `radix-nova`, not "default + slate".** The setup spec specified shadcn's classic "Default style + Slate base color." The shadcn CLI (≥4.x) replaced `--style` and `--base-color` with a preset list (Nova / Vega / Maia / Lyra / Mira / Luma / Sera / Custom); none are named "slate." We ran `shadcn init -b radix --css-variables -y` and got the `radix-nova` preset. The visual tokens it shipped are fully overridden in `src/app/globals.css`, so the preset choice is cosmetic-only — but any future `npx shadcn add <component>` will pull components written for the radix-nova variant.

- **Tailwind v4 with CSS-based `@theme`, not `tailwind.config.ts`.** The setup spec said "update `tailwind.config.ts`," but `create-next-app` now scaffolds Tailwind v4, which puts theme tokens in `globals.css` via the `@theme` directive. No `tailwind.config.ts` file exists. End result is the same — design tokens compile to Tailwind utilities and CSS variables.

### Phase 1.5 — DB setup

- **Prisma 7 architecture: schema has no datasource URLs; connection split between `prisma.config.ts` (CLI/migrations) and an adapter on `PrismaClient` (runtime).** The Phase 1.5 spec assumed Prisma 6's pattern of `url = env("DATABASE_URL")` and `directUrl = env("DIRECT_URL")` inside `schema.prisma`. Prisma 7 (installed v7.8.0) rejects both fields in the schema (error P1012). The new architecture: (a) `prisma.config.ts` declares `datasource.url = process.env.DIRECT_URL` for the CLI / migrations / studio (session pooler, port 5432, supports prepared statements); (b) `src/lib/prisma.ts` constructs a `@prisma/adapter-pg` adapter with `process.env.DATABASE_URL` (transaction pooler, port 6543 + `?pgbouncer=true&connection_limit=1`) and passes it to `new PrismaClient({ adapter })` for runtime queries. The two-URL pattern is preserved — just plumbed through two different files instead of one schema block. Adapter dependencies added: `@prisma/adapter-pg`, `pg`, `@types/pg`.

- **Prisma 7 client barrel.** Prisma 7's `prisma-client` generator emits the client into `src/generated/prisma/` as separate files (`client.ts`, `models.ts`, `enums.ts`, etc.) with no `index.ts`. To make `import { PrismaClient } from '@/generated/prisma'` resolve canonically (the idiom that tutorials and AI assistants assume), `scripts/post-prisma-generate.mjs` writes a barrel that re-exports from `./client`. The `prisma:generate` npm script chains generation + barrel; `postinstall` delegates to it so fresh clones always have a working barrel.

- **Public schema grants revoked from `anon` and `authenticated` roles.** Supabase's default setup grants table-level privileges on `public` to the `anon` (browser-exposed via `NEXT_PUBLIC_SUPABASE_ANON_KEY`) and `authenticated` roles. We don't use Supabase's REST/PostgREST endpoint at all — Prisma talks directly to Postgres through the pooler with the `postgres` role. So those grants were pure attack surface with zero benefit. Phase 1.5 ran:
  ```sql
  REVOKE ALL ON SCHEMA public FROM anon, authenticated;
  REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon, authenticated;
  REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM anon, authenticated;
  REVOKE ALL ON ALL FUNCTIONS IN SCHEMA public FROM anon, authenticated;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON TABLES   FROM anon, authenticated;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON SEQUENCES FROM anon, authenticated;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON FUNCTIONS FROM anon, authenticated;
  ```
  Verified via `has_table_privilege('anon', …, 'SELECT' | 'INSERT')` returning `false` for every check. **If we later want to use Supabase REST for any reason** (Supabase Auth client-side, Realtime, Storage public buckets, etc.), grants need to be re-applied per-table with appropriate RLS policies. Don't blindly `GRANT ALL`.

### Phase 1.6 — Auth

- **Tailwind v4 spacing namespace collision — named `--spacing-*` tokens NOT exposed via `@theme`.** DESIGN.md defines spacing as `xs/sm/md/lg/xl = 4/8/16/24/40px`, but Tailwind v4's size-keyword utilities (`max-w-md`, `max-w-lg`, `max-h-xl`, `min-w-sm`, etc.) read from the same `--spacing-*` CSS variable namespace. Defining `--spacing-md: 16px` in `@theme` would shadow Tailwind's default size-keyword resolution and make `max-w-md` = 16px instead of 28rem. Discovered during Phase 1.6 Task 5 when the login card rendered ~200px wide instead of ~450px. Resolution: we use Tailwind's **numeric** spacing utilities exclusively (`p-1` = 4px, `p-2` = 8px, `p-4` = 16px, `p-6` = 24px, `p-10` = 40px) — these derive from the singular `--spacing` base unit (`0.25rem`) and don't collide. Equivalents table is documented in `src/app/globals.css`.

- **Auth.js v5 module augmentation requires `@auth/core/*` paths, not just `next-auth/*`.** Auth.js v5's docs show augmenting `next-auth` and `next-auth/jwt` to add custom fields (e.g. `Session.user.role`, `JWT.role`). In beta.31 reality, the `next-auth/jwt.d.ts` file is `export * from "@auth/core/jwt"` — TypeScript interface merging doesn't propagate through the `export *` re-export. Augmentation must target both the wrapper paths (`next-auth`, `next-auth/jwt`) AND the originals (`@auth/core/types`, `@auth/core/jwt`). See `src/types/next-auth.d.ts` for the four-module declaration. Discovered Phase 1.6 Task 3 — initial spec-shaped augmentation produced TS2322 errors (`token.id` typed as `unknown`).

- **Next.js 16 middleware → proxy rename.** The original Phase 1.6 spec called for `src/middleware.ts`; Next.js 16 deprecated that convention in favor of `src/proxy.ts`. File contents are unchanged (the `auth((req) => …)` wrapper from Auth.js works identically). Critically, **`proxy.ts` defaults to the Node.js runtime** per the official docs, which solves the Auth.js + Prisma edge-bundling problem (the proxy import chain pulls in `@prisma/adapter-pg` → `pg` → `node:net` etc.) without needing to split auth config into `auth.config.ts` + `auth.ts`. Future contributors looking at Auth.js v5 docs will see the split-config pattern; **ignore it** — our stack doesn't need it. Discovered Phase 1.6 Task 4 when the dev server failed to compile middleware.ts under Edge Runtime.

### Phase 2.1 — Customers

- **Master data parties (Customers / Suppliers) are for regulars only — walk-in / one-time parties NOT represented in master tables.** Forcing every sale/purchase party through a master record creates friction that doesn't match jewelry-workshop reality. The dual-path party model lands in Phase 3 (Sales) and Phase 4 (Purchases): each Sale/Purchase row gets either `customerId` (FK to a known regular) OR a free-text `partyName` + `partyPhone` pair (one-time / walk-in). The Customers page therefore intentionally has no Excel-bulk-import yet; regulars are entered manually as they emerge. Discovered Phase 2.1 planning. Cross-references: Phase 3 / Phase 4 implement the autocomplete + free-text fallback.

- **Schema extraction pattern for forms with Server Actions.** Zod schemas cannot be exported from files carrying the `'use server'` directive — Next.js compiles non-function exports into client-reference stubs, replacing the actual schema with a serialized handle. When the client form modal imports the "schema," it receives a stub that fails the `zodResolver`'s `isZod4Schema` check (`'_zod' in schema`) at module load with **"Invalid input: not a Zod schema."** Convention going forward: each entity gets a `schema.ts` (no directive — pure validation), `actions.ts` (`'use server'`, imports schema), and form modal (`'use client'`, imports schema). **Same rule applies to type-only exports:** Phase 2.3 originally put `export type { EmployeeForClient }` inside `actions.ts` — Next.js's actions loader can't handle that either, producing a runtime `ReferenceError: EmployeeForClient is not defined` when the form modal imported it. Fix: move shared client-facing types (along with any serializer helpers like `serializeEmployee`) into a separate non-server module (`types.ts`). Pattern committed for Customer in Phase 2.1; Suppliers (Phase 2.2) and Employees (Phase 2.3) follow the same layout — Employees additionally has `types.ts` for `EmployeeForClient` + `serializeEmployee`. Cross-reference Sales (Phase 3) and Purchases (Phase 4) when those land. Discovered Phase 2.1 Task 7; type-export trap discovered Phase 2.3.

- **RHF triple-generic pattern for transform-emitting schemas.** When a zod schema uses `.transform(...)` (as ours does to coerce `""` → `null` on optional fields), the input and output types differ — `phone: string | null | undefined` going in, `phone: string | null` coming out. RHF v7's `useForm<TFieldValues>` defaults `TTransformedValues = TFieldValues`, which mismatches the resolver's actual return shape. The fix is the **explicit triple generic**: `useForm<FormInput, unknown, FormOutput>` where `FormInput = z.input<typeof schema>` (form's pre-transform value type, allows `defaultValues: { phone: '' }`) and `FormOutput = z.output<typeof schema>` (post-transform shape passed to `onSubmit`). Without it, TypeScript rejects both `defaultValues` and `handleSubmit`. Committed for the Customer form modal in Phase 2.1 Task 4; same pattern for every form modal going forward.

- **Optional-field edit semantics — empty form field means NULL, not "preserve old value."** Customer/Supplier/Employee input schemas use a `.nullish().transform((v) => (v === undefined || v === null || v === "" ? null : v))` pattern (with `.pipe(z.union([z.null(), z.string().email(...)]))` for email so format validation runs after the empty-string normalization). This emits `null` for cleared inputs. Prisma's `update.data` treats `undefined` as "skip this field" but `null` as "set column to NULL" — so emitting `null` makes clearing-via-edit-form actually clear the DB column, not silently retain the stale value. The previous `.transform(() => undefined)` pattern from the Phase 2.1 spec example had this bug. Output type for each optional field is `string | null`, never `string | undefined`. Discovered Phase 2.1 Task 3.

### Phase 2.2.5 — Test infrastructure

- **Test infrastructure: Vitest + mocked Prisma, no real DB.** All Phase 2.2.5 tests run against `vitest-mock-extended`'s deep-mocked PrismaClient (`src/lib/__mocks__/prisma.ts`); real-DB integration tests are deferred to Phase 8 polish. Component tests use `@testing-library/react` + `user-event` with mocked `next/navigation` and mocked server actions. **Mock at the closest meaningful boundary**: `vi.mock("@/lib/auth-guards", ...)` rather than `vi.mock("@/lib/auth", ...)` — smaller surface, single export, no Auth.js factory coupling. The schema/action/component category split + the canonical mock patterns are documented in `docs/TESTING.md`.

- **Three pre-test extractions to canonical helpers (Phase 2.2.5 Tasks 2–4).** Before tests were written, three patterns were extracted from the duplicated Customer/Supplier code so tests would validate the canonical code, not the duplication: (a) `requireSession()` → `src/lib/auth-guards.ts` (was inlined in two actions.ts files); (b) `<Field>` → `<LabeledField>` in `src/components/labeled-field.tsx` (was duplicated as ~25-line subcomponent in two detail modals); (c) form-control styling → `<FormLabel>` / `<FormInput>` / `<FormTextarea>` / `<FormError>` in `src/components/form-controls.tsx` (was four exported `FIELD_*` className constants per form modal, ~20 lines each). Net change: -32 LOC project-wide; each entity's form-modal dropped from 240 to 191 LOC.

- **Test mock reset conventions split by test category.** Action tests reset Prisma at module scope (`beforeEach(mockReset(prisma))` in `src/lib/__mocks__/prisma.ts`) and reset `requireSession` / `revalidatePath` at file scope. Component tests reset all mocks inside the `describe` block via `beforeEach(vi.clearAllMocks)`. Different mock surfaces (deep-mock vs shallow `vi.fn()`s), different reset semantics; both correct for their case. Don't mix the two reset approaches within one file. See `docs/TESTING.md` for the table.

### Phase 2.3 — Employees

- **Prisma enum value imports pull the entire Prisma client runtime into the client bundle.** Phase 2.3 originally had `import { EmployeeType } from "@/generated/prisma"` (value import) at the top of `schema.ts` plus a re-export for components. `EmployeeType` is a runtime const object in Prisma 7's client; the value import drags `@prisma/client/runtime/client.mjs` (which uses `node:module`) into every chunk that imports schema.ts. Through schema.ts → form-modal.tsx → page.tsx the Node-only module ended up in the client bundle, and the first GET /employees returned 500 with `Module not found: node:module`. Rule: **never `import { EnumName }` as a value from `@/generated/prisma`** in any module reachable from a client component. Use `import type { EmployeeType } from "@/generated/prisma"` for type-only references (stripped at compile time, zero runtime cost), and `z.enum(["FIXED", "LABOUR"])` with literal strings for runtime validation. Same rule applies to any Prisma runtime construct (`PrismaClient`, `Prisma.XyzScalarFieldEnum`, etc.) reachable across the boundary. Adjacent class of bug to the schema-extraction pattern above — both about "what gets pulled across the server/client boundary by an incidental import." Discovered Phase 2.3 build smoke.

- **BigInt currency fields stay BigInt only at the Prisma boundary — schema validates plain `number`, action converts at the edges.** `Employee.monthlySalary` is `BigInt? @map("monthly_salary")` in Prisma (paise integer math, future-safe for any salary range). The naive shape — a zod `.transform(v => BigInt(Math.round(v * 100)))` directly in the schema — broke client→server saves: the client form's `handleSubmit` produced a BigInt, then passed that BigInt to the server action, which re-ran `safeParse(input)` and rejected the BigInt with `Expected number, received bigint`. The fix is a three-layer pipeline: (a) **schema** validates rupees as `z.number().int().positive().nullish()` — input AND output shapes are both `number | null`, so client send + server re-parse stay aligned; (b) **action** has a local `toPrismaData()` / `buildSaleData()` helper that converts rupees → `BigInt(Math.round(value * 100))` paise at the Prisma boundary only; (c) **action return** runs a `serializeEntity()` helper from `types.ts` / `sale-helpers.ts` that converts the Prisma row's BigInt back to `number` for JSON safety, returning `EntityForClient` instead of the raw row. JSON cannot encode BigInt; React Server Components' Flight serializer cannot either. **General rule for any future BigInt column**: keep the wire format JSON-safe at both client/server crossings; do the BigInt conversion exactly at the Prisma write and undo it exactly at the action's return. Discovered Phase 2.3 build (Playwright smoke caught the wire-format mismatch). **Extended Phase 3.1** to the Sale entity — three BigInt columns per row (`rate`, `discount`, `total`) all flow through the same pipeline: schema keeps them as `z.number().nonnegative()`, `buildSaleData()` does the BigInt conversion *and* computes the stored total in BigInt math, `serializeSale()` returns `Number` to the client. Every subsequent monetary field in Phase 3.2+ / Phase 4 / Phase 6 follows the same shape.

### Phase 3.1 — Sales

- **Dual-path party model on `Sale` — denormalized snapshot + nullable FK.** The Sale row has three party-related columns: `customerId` (FK to `Customer`, nullable, `onDelete: SetNull`), `partyName` (required string), and `partyPhone` (optional string). Three operating modes: (1) **linked customer** — `customerId` is set and `partyName`/`partyPhone` are *server-side snapshots* of `Customer.name` / `Customer.phone` at sale time. The form may pass values for these fields, but the action's `buildSaleData()` overwrites them by re-reading the customer row (server is source of truth for FK-linked party data); (2) **walk-in** — `customerId` is null and the two strings are the only identity; (3) **defensive** — if a customer is ever hard-deleted (currently only soft-delete exists, but the FK behavior should survive future schema changes), `onDelete: SetNull` zeroes the FK while leaving `partyName`/`partyPhone` intact, so sale history is preserved. Snapshot pattern is what lets a customer rename (e.g. typo fix) without retroactively rewriting historical sale displays — the row carries the name as-of-the-sale. Discovered Phase 3.1 planning; matches the "regulars only" Phase 2.1 reframe — see the earlier "Master data parties" entry.

- **`Sale.total` is stored at write time, not derived on read.** Computed in the action's `buildSaleData()` helper as `BigInt(qty) × ratePaise − discountPaise` and persisted as a BigInt paise column. Alternative — compute on read — would be simpler at the action layer but loses audit history: if the discount/total logic ever changes (e.g. rounding rules, future per-line-item structure), historical sales would silently shift to the new formula. Stored totals also enable straightforward `SUM(total)` aggregations for dashboards / reports without expression complexity. Trade-off: total must be recomputed on every `updateSale`, and the discount-exceeds-line-total guard fires at the action layer (not the schema) because the formula needs the parsed numbers in scope. Acceptable for ~100 sales/month. Status remains derived (see CLAUDE.md §5) — different concern: status reflects payment/return state which DOES change over time, total reflects the original transaction terms which shouldn't. Discovered Phase 3.1 planning.

### Phase 3.2 — Sale payments

- **Per-payment audit trail via `SalePayment` child table — aggregation over column.** Phase 3.2 stores each payment as a separate row in `sale_payments` with `saleId` FK (`onDelete: Cascade`), `amount` BigInt paise, and the standard soft-delete column. `paidAmount` per sale is derived live via `SUM(SalePayment.amount WHERE deletedAt IS NULL)`, never cached on `Sale`. **Rejected alternative**: cached `paidAmount` column on `Sale` updated via trigger or action — adds drift risk (action forgets to update on a path; trigger gets bypassed by raw SQL fix-ups) for negligible aggregation cost at the scale we're at (~100 sales/month × handful of payments each = ~300 SUMs per page render, easily under 10ms with the `@@index([saleId])`). Per-row history is essential for the business — "when did the customer last pay you, and how much?" is the core question this entity exists to answer. Status derives via the same shape — `computeSaleStatus` reads `paidAmount` aggregation + (future) `returnTotal` aggregation, never a stored status field. Discovered Phase 3.2 planning.

- **Overpayment blocked at the action layer, NOT the schema.** Payments exceeding `total − paidAmount` are rejected by `createSalePayment` with `{ ok: false, errors: { amount: ["Exceeds remaining balance. Outstanding: ₹X"] } }` — the formatted outstanding helps the user identify what would have been accepted. **Why action and not schema**: the constraint needs the parsed `amount` + the sale's `total` + the current sum-of-payments in scope; the schema doesn't query the DB. **Why block at all** (vs. allowing overpayment with refund_due status): in practice, overpayment is either (a) a data entry error — catch it immediately and force the user to confirm intent; or (b) the customer paid extra and a refund is owed — which is a return-driven flow handled in Phase 3.3 via `SaleReturn`. Conflating "overpaid by mistake" with "customer overpaid intentionally" would lose the distinction. **`refund_due` status is reserved for return-driven refunds, never payment-driven overpayment.** Cross-reference: Phase 3.3 will add `SaleReturn` and `returnTotal` aggregation; `refund_due` activates there. Discovered Phase 3.2 planning.

- **Payments are immutable — soft-delete + create new, no update.** No `updateSalePayment` action exists. To correct a wrong payment: soft-delete the bad entry (sets `deletedAt`; row stays in the table but is filtered out of `paidAmount` aggregation via `WHERE deletedAt IS NULL`) and create a new correct payment. Both events stay in the history list visible in the detail modal's payment panel. **Why**: preserves audit trail (you can see "wrong ₹500 entry was reversed, replaced with ₹450") — important when reconciling with the customer's own records. **Trade-off**: slightly more UI work for corrections; the user clicks × on the bad row and creates a new one rather than editing in place. The Phase 3.2 inline panel makes this two-click flow ergonomic — × → Confirm reverse → form already expanded with "Pay full balance" ready. Discovered Phase 3.2 planning.

- **Live-updating modal pattern — derive viewed entity from id + parent data, not local snapshot.** When a detail modal shows data that can change via inner UI actions (Phase 3.2: payments; Phase 3.3: returns; Phase 3.4: receipts; future status/balance changes), holding the entity as `useState<EntityForClient>(viewing)` makes the modal show **stale** data after `router.refresh()` — the parent re-fetches, but the modal's local state still references the pre-mutation object. **Canonical fix**: `useState<string | null>(viewingId)` + derive via `parentDataArray.find(x => x.id === viewingId) ?? null`. After mutations call `router.refresh()`, the parent re-fetches → the derived value automatically resolves to the *updated* row → modal re-renders with fresh status / paidAmount / payments / chip in title — all without close-and-reopen. See `sales-table.tsx` Phase 3.2 implementation as the canonical example. **Use this pattern for Phase 3.3's return panel and Phase 3.4's receipt panel**, plus any future inline-edit-in-detail flows. The Phase 3.1 `viewingSale` state worked because nothing inside that modal mutated it; Phase 3.2's payment-panel broke that invariant, so the pattern needed to change. Discovered Phase 3.2 build (Playwright walkthrough's Step 5 critical assertion would have caught the bug if I hadn't fixed it preemptively).

### Phase 3.3 — Sale returns + refunds

- **`SaleReturn` as a separate child table, not negative-direction `SalePayment` entries.** Returns are conceptually distinct from payments: one represents "product back," the other "money flow." Mixing them in `SalePayment` would have required type-discrimination on every query and lost the audit-category distinction — "show all returns this month" would become a filter-then-aggregate instead of a direct query. Separate `sale_returns` table preserves the categorical split and keeps two clean per-sale aggregations: `returnTotal = SUM(SaleReturn.refundAmount)` (product side, value-out) vs. `paidAmount = SUM(SalePayment.amount WHERE type=PAYMENT) − SUM(... type=REFUND)` (money side, net). Pattern matches Phase 3.2's `SalePayment`-as-child-table reasoning — aggregate-on-read beats cached columns for the workshop-scale workload. Discovered Phase 3.3 planning.

- **Refunds as `REFUND`-type `SalePayment` entries, NOT a separate `SaleRefund` table.** A refund IS a payment in the opposite direction. Same form (date + amount + note), same workflow (record event + soft-delete + recreate for corrections), same audit history. Adding a `type` enum (`PaymentType { PAYMENT, REFUND }`) on `SalePayment` keeps the payment ledger unified — users always see "Customer paid ₹2,400 on Mar 1, refunded ₹400 on Mar 5" as a single chronological stream. Net `paidAmount = SUM(PAYMENT.amount) − SUM(REFUND.amount)`, both filtered for non-deleted. **Rejected alternative**: a parallel `sale_refunds` table that fragmented the payment history into two streams users would always want to view interleaved. The Phase 3.3 migration adds the `type` column with `@default(PAYMENT)` so existing Phase 3.2 rows backfill correctly (verified via Supabase MCP: 3 pre-existing rows all backfilled to `PAYMENT`, 0 `NULL`, 0 `REFUND`). Single table + discriminator is cleaner. **Note**: this differs from `SaleReturn` (separate table) because Returns and Payments are categorically different concerns, while Payments and Refunds are the same concern in opposite directions. Discovered Phase 3.3 planning.

- **`refund_due` fires on `paidAmount > effectiveTotal` (where `effectiveTotal = total − returnTotal`).** Clean semantic: "the customer has paid more than the now-reduced amount owed." This is the only condition that triggers `refund_due` — pre-Phase-3.3 placeholder logic in `computeSaleStatus` triggered on `balance < 0` which was conceptually the same thing but worded around payments, not returns. The Phase 3.3 rewrite makes the return-driven causation explicit. **Edge case**: full return with no payment (`returnTotal === sale.total, paidAmount === 0n`) resolves to `completed` (sale is closed, nothing was ever owed back) — the `returnTotal > 0n` guard distinguishes "fully returned" from "degenerate ₹0 sale" (which stays `pending`). The full-return-no-payment case is unreachable in production because `createSaleReturn` validates cumulative `refundAmount ≤ sale.total`, but the function handles it gracefully for direct-API safety. Discovered Phase 3.3 planning; tested across 16 sale-status boundary cases.

- **Returns are immutable — soft-delete + create new (same as payments).** No `updateSaleReturn` action exists. Wrong return → soft-delete the bad entry (sets `deletedAt`; row stays but is filtered out of `returnTotal` aggregation) + create new correct return. Audit trail preserved. **Cross-row status interaction**: soft-deleting a return changes `effectiveTotal` which can flip status in either direction — `refund_due → completed/partial` when undoing a return whose refund hadn't been issued yet, `completed → partial` when undoing a return that had reduced effectiveTotal to match paidAmount, etc. Same applies to soft-deleting a `REFUND`-type `SalePayment` (Phase 3.3 walkthrough Step 12 exercises this: a sale that's `completed` after refund issuance flips back to `refund_due` if the refund payment is soft-deleted while the return remains active). The `viewingSaleId` live-update pattern handles the chip recomputation without modal close-and-reopen. Discovered Phase 3.3 planning.

### Phase 4 — Purchases

- **Unified `computeTransactionStatus` helper for Sales + Purchases.** Phase 4 introduced Purchases as a structural mirror of Sales. The status math is identical across both entities (`pending` / `partial` / `completed` / `refund_due` derived from `total`, net `paidAmount`, `returnTotal`) — no entity-specific divergence in thresholds or edge cases. Decision: rename `src/lib/sale-status.ts` → `src/lib/transaction-status.ts`, rename `computeSaleStatus` → `computeTransactionStatus`, keep `SaleStatus` and `PurchaseStatus` as **type aliases** in each entity's helpers (`sales/sale-helpers.ts` re-exports `type SaleStatus = TransactionStatus`; `purchases/purchase-helpers.ts` declares `export type PurchaseStatus = TransactionStatus`) for call-site readability. **Rejected alternative**: a thin `purchase-status.ts` that just re-exports the Sales helper — adds ceremony with no benefit since the math is genuinely shared. **Rejected alternative B**: two parallel implementations — invites silent drift if one is patched without the other. **Trade-off**: tight coupling between Sales and Purchases status logic. **Rationale**: divergence in status rules between sales and purchases is implausible at this scale; if it ever happens, the single file is the obvious extension point with predictable refactor cost. The unified `<TransactionStatusChip>` (in `src/components/`, not in either entity folder) follows the same pattern — single component, both folders import it. Discovered Phase 4 planning.

- **UI label inversions for supplier-direction (Purchases) — same enum, same status, opposite money direction.** Phase 4 introduced semantic inversions where the same `PaymentType` enum + same `refund_due` status mean opposite money-direction depending on which entity owns the row. The mental model that ties it together: **red = money OUT of shop; blue/secondary = money IN to shop, regardless of which entity owns the row.** Concrete inversions wired into `purchases/payment-panel.tsx`:
  - "Outstanding" (Sales: customer owes shop) → "Owed to supplier" (Purchases: shop owes supplier)
  - "Refund owed" (Sales: shop owes customer back) → "Refund expected" (Purchases: supplier owes shop back)
  - Indicator color when refund_due fires: `text-error` (red, Sales) → `text-secondary` (blue, Purchases) — money IN is positive
  - Trigger button label when refund_due fires: "+ Issue refund" (Sales) → "+ Record refund received" (Purchases)
  - REFUND-row label in history: "Refund" (Sales) → "Refund received" (Purchases)
  - REFUND-row text color: `text-error` (Sales) → `text-secondary` (Purchases)
  - REFUND-row amount prefix: `−` (Sales: money out) → `+` (Purchases: money in)
  - Server error message in `payment-actions.ts` overpayment rejection: "Outstanding: ₹X" (Sales) → "Owed to supplier: ₹X" (Purchases)

  The label inversions are the **most visible Sales-vs-Purchases difference** from the user's perspective; the schema clones cleanly, the actions clone cleanly, but copy-paste regressions in the UI would silently leak Sales-direction language into the Purchases panels. The Phase 4 walkthrough's Step 7 + Step 11 explicitly assert on the inverted labels (and the `payment-panel.test.tsx` does dual-assertion: positive on the new label + negative on the old). Discovered Phase 4 planning.

- **`<PartyPicker>` now exists twice (Sales + Purchases) — deliberately NOT extracted.** Both `sales/party-picker.tsx` and `purchases/party-picker.tsx` are ~177-line structural clones with parameter substitution (`customerId ↔ supplierId`, `customers ↔ suppliers` prop, `CustomerOption ↔ SupplierOption`, `"Customer name or walk-in" ↔ "Supplier name or walk-in"`, `"Clear linked customer" ↔ "Clear linked supplier"`). **Rejected alternative**: extract now to `<PartyPicker directory={Array<{id, name, phone | null}>} valueShape={...} />` after two instances. **Why hold off**: with only two data points (master-data customers, master-data suppliers), the right abstraction shape isn't clear — what fields belong on `directory` items? does the picker need to know the entity name for placeholder/aria text, or does the parent inject those? **Extraction trigger**: Phase 6 (karigar payments) is likely to add the third party-picker instance for selecting an employee/karigar from the `employees` table. At that point three concrete instances will make the right generic shape obvious. Premature abstraction across two instances risks locking in a shape that breaks for the third — and the cost of carrying the duplication for one more phase is bounded (177 lines × 2 files). ### Phase 5 — RBAC (four roles)

- **Four-role enum replacing `ADMIN | STAFF`.** Phase 5 replaced the binary role split with four explicit roles matching the company's operational shape: `ADMIN` (full access), `PURCHASE_DEPT` (Purchases + Suppliers full CRUD), `LABOUR_MGMT` (Employees full CRUD including salaries — strictly no Sales/Purchases visibility), `CASTING_PLATING_MGMT` (Casting + Plating routes; pages deferred to Phase 9). `STAFF` removed entirely — was never used in production (verified zero rows before drop). `User.role` is required-on-insert (no DB default); every new user must explicitly choose a role. Migration applied via two SQL files: `20260515182838_role_add_new_values` (additive `ADD VALUE` × 3) + `20260515183353_role_remove_staff` (CREATE new type → ALTER COLUMN → DROP old type, hand-rolled because non-interactive shells can't satisfy `prisma migrate dev`'s breaking-enum confirmation prompt). Discovered Phase 5 planning.

- **`requireRole(allowedRoles[])` pattern at every server action.** Replaces per-action `requireSession()` for role-gated actions. The signature is `requireRole(allowedRoles: Role[]) => Promise<Session>`; throws `Unauthorized` (no session) or `Forbidden` (wrong role); both halt before any DB work. Pattern at every action: `await requireRole(["ADMIN", "PURCHASE_DEPT"])` as the first await. **Why explicit at the call site**: reading the action's first line tells you exactly which roles can invoke it — the access matrix is local to the action, not buried in a shared config. **Why kept `requireSession()`**: still useful for endpoints where any authenticated user is sufficient (currently none — Phase 5 migrated everything, but the helper stays for one-off cases). Definition lives in `src/lib/auth-guards.ts`. Discovered Phase 5 planning.

- **Defense in depth for route access — sidebar filters AND proxy redirects.** UX layer: `src/app/(app)/sidebar.tsx` filters `NAV_ITEMS` by `user.role.allowedRoles.includes(...)` so users never see options they can't use. Security layer: `src/proxy.ts` carries a `ROUTE_ROLES` map; unauthorized URL access (manual typing, bookmarks, deep links) bounces to `/dashboard` before any page module loads. **Both required**: sidebar alone leaves manual-URL access unblocked; proxy alone leaves stale nav items in the UI. The matrix is duplicated in three places — proxy's `ROUTE_ROLES`, sidebar's `NAV_ITEMS[].allowedRoles`, and per-action `requireRole([...])` calls — accepting some redundancy to keep each layer's rules local and readable. If the matrix grows complex enough that drift becomes a real risk, extract to a single source-of-truth `src/lib/rbac-matrix.ts` and have all three layers consume it. Not worth doing yet at four roles × ~8 routes. Discovered Phase 5 planning.

- **Single `/dashboard` route with role-aware server-side rendering.** Not multiple routes (`/dashboard/admin`, `/dashboard/purchase`, etc.). The page reads `session.user.role` and `switch`es to one of `AdminDashboard | PurchaseDashboard | LabourDashboard | CastingPlatingDashboard`, each a server component that fetches only the data its cards need. **Why single route**: simpler URL structure (every role lands on the same path after login, so `proxy.ts` can put `/dashboard` in `ROUTE_ROLES` once with all four roles); centralised role-switching logic; bookmarks survive role changes (admin demoted to PURCHASE_DEPT keeps `/dashboard` bookmark working). Trade-off: a single switch statement that has to stay exhaustive — TypeScript catches non-exhaustive switches via the `never` assignment in the default branch. Discovered Phase 5 planning.

- **Phase 5 ships minimal landing pages; full Recharts dashboards deferred.** Each role gets a welcome header + 2–4 summary cards (counts, current-month totals, "owed to suppliers" for the purchase role). No Recharts, no monthly trend lines, no payable timelines, no aging buckets. Real charting (monthly sales trend, supplier payable aging, salary expense trend) is deferred until Phase 11 (full Recharts dashboards from original plan). **Why defer**: the right charts depend on real usage data informing which views matter — three months of production transactions tells us more than upfront design. Cards exist now to give every role somewhere to land after sign-in; charts join when the user has real data to plot. Discovered Phase 5 planning.

### Phase 6 — Walk-in auto-promotion

- **Walk-in auto-promotion via phone identity (Phase 6).** When a sale or purchase is saved as walk-in (no explicit `customerId`/`supplierId`) but WITH a populated `partyPhone`, the server transactionally either links to an existing Customer/Supplier (matched by normalized phone) or auto-creates one. Walk-ins without phone stay as snapshot-only entries — no auto-creation since identity cannot be confirmed. The whole flow (`tx.customer.findFirst` → optional `tx.customer.create` → `tx.sale.create`) runs in `prisma.$transaction`, so customer/supplier creation and sale/purchase creation succeed or fail together. **Rationale**: user-stated workflow problem — *"if I enter xyz in sales as walkin it should be updated into the customers same for purchase so that the name does not change if they are same"*. Phone is the most reliable identity proxy at this workflow's scale (~100 transactions/month, small known party list, no GST/PAN identifiers tracked yet). The action *also* re-snapshots `partyName` from the canonical Customer/Supplier row on every save — so the second walk-in with the same phone but a different typed name carries the canonical name, not the new typed string. Discovered Phase 6 planning; verified end-to-end via the production walkthrough's step 2.

- **Phone normalization at every boundary (Phase 6).** `normalizePhone(s)` in `src/lib/phone.ts` strips whitespace, dashes, and parens; preserves leading `+` for international format; returns `null` for empty/whitespace-only input. Idempotent — running normalization on already-clean input is a no-op. Applied at **every storage boundary** (`Customer.phone`, `Supplier.phone`, `Sale.partyPhone`, `Purchase.partyPhone` schema transforms) AND at **every lookup boundary** (auto-promotion `findFirst` queries, party-picker phone-prefix matching). Without symmetric normalization, lookups miss already-stored records (typed `9876-543-210` would not match stored `9876543210`). The `+`-preservation is deliberate: international numbers with a leading `+` are kept distinct from the same digits without `+`, so `+919876543210` and `919876543210` would NOT match each other — accepted trade-off, no current Indian-only workflow uses the leading `+`. Discovered Phase 6 planning.

- **Party picker phone-prefix matching (Phase 6).** Typing digits into the party picker now surfaces customers/suppliers whose **normalized phone starts with** the typed prefix, in addition to the existing name-substring match. **Pure-letter queries skip phone matching entirely** (the picker only considers phone candidates when the query contains at least one digit) — avoids spurious hits if a stored phone ever happened to contain letters. Mixed-alphanumeric queries match by name only (the query is treated as a name substring; the picker doesn't try to extract digits from a mixed string). Both the candidate phone and the query digits are run through `normalizePhone` before comparing, so `9876-543-210` stored matches `9876` typed and vice versa. The "Use as walk-in: …" footer entry stays at the bottom regardless of match results. Discovered Phase 6 planning.

### Phase 7 — Multi-item line items

- **Multi-item line items via child tables (Phase 7).** `SaleLineItem` and `PurchaseLineItem` tables, one row per line item, FK to parent with `onDelete: Cascade`. **Rejected alternatives**: (a) JSON column on parent — makes aggregation queries painful ("total revenue by item type" becomes JSON traversal instead of JOIN); query-tooling support degrades; types lose precision since JSON columns can't enforce `BigInt`/integer constraints. (b) Single denormalized item per parent — the Phase 3.1 lock that real usage proved wrong within four phases. The chosen child-table pattern matches every other relational shape in this codebase (payments, returns) and lets the same `prisma.$transaction(tx => ...)` wrapper handle the create/update flow with no new infrastructure. Discovered Phase 7 planning.

- **Sale-level discount only, no per-line discount (Phase 7).** `Sale.discount` and `Purchase.discount` apply to the whole-sale subtotal; `SaleLineItem`/`PurchaseLineItem` carry only `itemDescription`, `qty`, `rate` — no discount column per line. **Rationale**: matches the workshop's actual invoicing practice ("₹13,500 of items, give it for ₹13,000" — the discount is whole-invoice, not per-line). Per-line discount would force the user to decide which line absorbs the discount; that decision has no business meaning when the discount was negotiated against the whole sale. **If per-line negotiated discounts surface as a real workflow later**, the schema extends naturally with a `SaleLineItem.discount` column (and the action's subtotal math becomes a per-line `(qty × rate - discount)` sum). For now: `Sale.total = SUM(lineItems.qty × lineItems.rate) - Sale.discount`. Discovered Phase 7 planning.

- **Line items hard-deleted on parent edit — replace-all pattern (Phase 7).** Update sequence: `tx.saleLineItem.deleteMany({ where: { saleId } })` then `tx.sale.update({ data: { lineItems: { create: [...] } } })` inside `prisma.$transaction`. **Rejected alternative**: soft-delete each line item with `deletedAt` + diff-then-update — adds `deletedAt IS NULL` filters everywhere with no audit value (line items are subordinate to the parent Sale/Purchase; the audit-relevant unit is the parent transaction, not its line breakdown). **Sale soft-delete still preserves line items** in DB because `onDelete: Cascade` fires only on actual delete; soft-delete sets `deletedAt`, the line items remain attached and are filtered out of the app by the parent query's `deletedAt: null` clause. Hard-delete (which the app never performs) would cascade and remove the lines. Pattern atomically replaces the entire line set on every edit — no diffing, no per-line update logic, no edge cases around "what if the user removed a line that has dependent rows." Discovered Phase 7 planning.

- **Phase 3.1's single-item decision proved wrong by real usage — institutional-memory note (Phase 7).** The Phase 3.1 lock said "single qty/rate/itemDescription per Sale because the current workflow does one-item invoices." Real production usage produced multi-item invoices within four phases (the "fzd / sdf + 2 more" stray row was the first sign), forcing the Phase 7 restructure with two migrations and a major UI rebuild. **Cost**: ~6 hours saved in Phase 3.1, ~8 hours spent in Phase 7 to undo + rebuild + migrate data + rewrite 144 tests. **Net**: slightly negative on the bookkeeping; the alternative (over-engineering line items in Phase 3.1 before knowing the workflow needed them) might have produced an abstraction that didn't match the eventual shape either. **Tentative rule**: schema-shape decisions justified by "current workflow doesn't need this" should be revisited after real production usage, not before; locking them too early commits to a shape before the workflow is known. **Counter-rule**: don't add flexibility unprompted — three similar lines is better than a premature abstraction. The honest answer is the locks are right in expectation, sometimes wrong in retrospect; document the lineage so the same trade-off isn't re-evaluated from scratch every time.

### Phase 8 — Bills / R2 upload

- **Bill discriminator pattern over polymorphic FK (Phase 8).** One Bill table that can attach to multiple parent kinds (Purchase, PurchasePayment, CastingEntry, PlatingEntry, ...) had two shapes available: (a) a separate `*_bills` join table per parent kind, each with a real FK + CASCADE; (b) one Bill table with a string discriminator (`attachedToType`) + an unconstrained `attachedToId` carrying the parent's cuid. **Chose (b)**: adding a new attached-to kind in a future phase = extend the `ATTACHED_TO_TYPES` enum in `src/app/(app)/bills/schema.ts` + add a row to the role matrix in `src/lib/bill-access.ts`. The Bill table itself never changes shape, and the access matrix is the single source of truth for who-can-see-what. **Trade-off accepted**: no DB-level cascade on parent delete — orphan reference detection is the caller's responsibility. At ~100 transactions/month with rare hard deletes (everything is soft-delete), the orphan window is tiny; a deferred cleanup job (see Deferred items) can reconcile if needed. The polymorphic-FK alternative would have required 4+ join tables today and another every time a new kind is added. Discovered Phase 8 planning. *Note: Bill table was renamed to Attachment in polish session; pattern unchanged.*

- **R2 key includes a UUID independent of the Bill row id (Phase 8).** The natural shape would be `bills/YYYY/MM/<billId>-<filename>`, but Prisma's `@default(cuid())` generates the row id at INSERT time — and `r2Key` is `@unique` and required-non-null on the same insert. Pre-allocating a cuid client-side would either need a dependency on `@paralleldrive/cuid2` (not currently installed) or a homegrown cuid-shaped generator (rejected — reinvents the wheel). **Chose** `crypto.randomUUID()` for the key suffix: stdlib-only, collision-free at our scale, and decouples the R2 key from the Bill id so the action stays a single Prisma roundtrip. The Bill row's `id` and the key's UUID serve different purposes (DB PK vs. object name uniqueness); `@@unique` on `r2Key` is the DB safety net against collision. Discovered Phase 8 build.

- **R2 client construction is lazy (Proxy) — same rationale as the Prisma wrapper (Phase 8).** `src/lib/r2.ts` mirrors the lazy-init Proxy from `src/lib/prisma.ts`: env (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, etc.) is read on first property access, not at module load. Eager construction would crash Next.js 16's build-time page-data collection — the route module that imports `r2.ts` (via the Bill server actions) loads during static analysis, before runtime env-var injection. The pattern is now general: any SDK client wrapper that reads env vars at construction time should defer via Proxy. Documented in the §6 conventions as a general rule. Discovered Phase 8 build (verified by `next build` smoke).

- **Cloudflare R2 CORS configured via the S3 API, required an Admin-scope R2 token (Phase 8).** Browser → R2 PUT via presigned URL fails the CORS preflight without an explicit bucket CORS policy (the standard "Network error" symptom — `xhr.onerror` fires but the browser surfaces no actionable detail). Cloudflare R2 supports CORS configuration via the S3-compatible `PutBucketCors` command, BUT the credentials must come from an **Admin Read & Write** R2 token; the **Object Read & Write** token the app uses for presign + delete gets `AccessDenied`. **Resolution**: upgrade the token to Admin R&W temporarily, apply CORS, then revert the production env (Vercel + `.env.production.local`) to Object R&W (CORS rules persist independent of the token that set them). One-time setup; ongoing app traffic only needs Object R&W. Allowed origins applied: prod alias, git-main alias, `https://*.vercel.app` (preview deploys), `http://localhost:3000`, `http://localhost:3001`. Allowed methods: GET / PUT / HEAD / DELETE. Max age 1h. Discovered Phase 8 walkthrough.

### Phase 9 — Casting / Plating

- **Casting and plating as two separate entity types, not a unified table with a discriminator (Phase 9).** `CastingEntry` and `PlatingEntry` are structurally identical mirrors but live in their own tables (plus their own `*LineItem` + `*Payment` child tables). The unified-table alternative (one `OutsourceEntry` with `type: 'CASTING' | 'PLATING'`) was rejected: separate sidebar entries match separate workflow concepts in the workshop's mental model; per-entity URLs (`/casting`, `/plating`) are cleaner; per-entity action surfaces don't need a runtime branch on type; and future outsource categories (polishing, welding) extend by adding new entity types rather than overloading a discriminator column. **Trade-off accepted**: ~2,300 LOC of mirrored code per side. **Mitigation**: a reproducible mirror script (`scripts/_mirror-casting-to-plating.mjs`, gitignored under `scripts/_*.mjs`) generates plating files from casting with a protected-identifier substitution. Run after any casting-side change to keep plating in lockstep; verify post-mirror with `tsc --noEmit` + a grep for stray `casting`/`Casting` tokens outside the protected list. Discovered Phase 9 planning.

- **Single shared `CastingPlatingVendor` table covers both workflows (Phase 9).** Real outsourcing vendors often do both casting AND plating, so separate `CastingVendor` + `PlatingVendor` tables would have produced duplicate records for every overlapping vendor. The entry's table (`CastingEntry` vs `PlatingEntry`) determines the workflow; the vendor record is the same person/shop regardless. `CastingPlatingVendor` has both `castingEntries: CastingEntry[]` and `platingEntries: PlatingEntry[]` reverse relations; the vendors list page shows precomputed counts of each per row. Trade-off: the table name is awkward ("CastingPlatingVendor"); reading it as "vendor shared by casting and plating" is the intent. If a third workflow lands (polishing, etc.) we either rename or accept the cumulative name. Discovered Phase 9 planning. *Note: Phase 17a consolidated CastingPlatingVendor into the unified Party table with `isCastingVendor` + `isPlatingVendor` flags.*

- **Weight stored as `Decimal(10, 3)` kg, not Int grams (Phase 9).** Money in this codebase is stored as `BigInt` paise (integer-storage pattern) — applying that consistency to weight would have meant `BigInt` grams (e.g., 2500g for 2.5kg). **Rejected**: the workflow speaks kg (the user reads "2.5 kg" not "2500 g"), invoices speak kg, and forcing a g↔kg conversion at every read+write boundary would add complexity without ergonomic upside. `Decimal(10, 3)` enforces the 3-decimal-place gram precision at the column level; `Decimal.js` handles arithmetic exactly. The pattern is symmetric with money (storage primitive that needs precision preservation) but uses a different primitive (`Decimal` for fractional units, `BigInt` for integer units). Discovered Phase 9 planning.

- **Rate stored as `BigInt` paise per kg — money pattern preserved (Phase 9).** Weight is `Decimal`; rate is `BigInt`. The Decimal × BigInt multiplication lives in exactly one place: `computeLineTotal(weightKg, ratePerKg): bigint` in `src/lib/weight-helpers.ts`. The helper does `weightKg.mul(ratePerKg.toString()).toDecimalPlaces(0, ROUND_HALF_EVEN)`. **ROUND_HALF_EVEN** (banker's rounding) was chosen over ROUND_HALF_UP — banker's rounding has no systematic bias when summing many rounded values (each `0.5` case rounds to the nearest even, balancing out across the dataset), while half-up biases positive over many transactions. At ~50 casting/plating entries per month with multiple line items each, the bias accumulates measurably over a year. **Verified via the 4 distinguishing cases** in `weight-helpers.test.ts` (`0.5→0`, `1.5→2`, `2.5→2`, `3.5→4`). Discovered Phase 9 planning.

- **Decimal columns serialise as strings (not numbers) at the action boundary (Phase 9).** `CastingLineItem.weightKg` reads as a Decimal in Prisma, serialises to a `string` (e.g., `"2.500"`) at the action's `serialize*Entry()` return, and the client formats via `formatKg(string)` for display. The naïve alternative — `Number(weightKg.toString())` at the boundary — collapses `"2.500"` to `2.5` and loses the gram-precision contract that the DB column enforces. JS Number can represent `2.500` numerically (it's an exact float) but cannot distinguish it from `2.5` once stringified; the string preserves the original digit shape. Symmetric pattern with BigInt → Number paise serialisation (both are "storage primitives that need precision preservation across the JSON wire"). Discovered Phase 9 build (would have shipped `2.5 kg` instead of `2.500 kg` in the table view otherwise).

- **No returns workflow for casting / plating (Phase 9).** Outsourced services don't have a returnable-goods analogue to `SaleReturn` / `PurchaseReturn`. The vendor performs a service; if the result is unsatisfactory, the typical remedy is rework (no money changes hands) or a refund (handled as a `REFUND`-type `CastingPayment` / `PlatingPayment`, mirroring the Sale / Purchase refund pattern via the shared `PaymentType` enum). **Rejected** the `CastingReturn` table because there's no defective-goods workflow to track quantitatively — the underlying entity is a job, not units. **Trade-off**: the `computeTransactionStatus` call site for casting/plating doesn't pass a `returnTotal` argument (defaults to `0n`), so `refund_due` only activates if a REFUND-type payment over-applies relative to the entry total. In practice this is rare; it's there for symmetry with the existing status machine. Discovered Phase 9 planning.

### Phase 10 / 10.5 / 10.6 — Form-as-page UX

- **Forms moved to dedicated pages — Sales-only scope this phase (Phase 10).** The modal pattern outgrew multi-line forms when Phase 7 added line-item arrays — modal width + native scrolling + browser-history were all cramped. Form-as-page gives full-width layout, native scrolling, browser back/forward, and bookmarkable URLs. **Scoped to Sales** for Phase 10 per the explicit scope decision at build start; Purchases / Casting / Plating mirror lands in Phase 10.5 (mechanical, the shared components are proven). **Detail modal stays as a modal** even after the form moved — it's a small read-only surface where the modal pattern still works; converting it to a page would have meant a separate `/sales/[id]` route just to view, which doesn't add value. Discovered Phase 10 planning.

- **Detail modal → read-only (Sales, Phase 10).** Separates view from write. The modal previously carried four mutation responsibilities (Add Payment, Add Return, Replace Bill, Delete) which made it the de-facto workflow center; the user had to know to "open detail" to do anything. The new pattern: detail modal answers "what's in this sale?" (read-only line items, payments history, returns history, status chip); the row's Actions column answers "what do I want to change?" (`$ Pay` / `📎 Bill` / `↩ Return` icon buttons + the Edit link → `/sales/[id]/edit`). Cleaner mental model. **Purchases / Casting / Plating detail modals retain their mutation surfaces (PaymentPanel, ReturnPanel, embedded bill section) until Phase 10.5.** Discovered Phase 10 walkthrough Step 4 — explicitly verified zero mutation buttons inside the new sales detail modal.

- **Inline action buttons on transaction rows — three slots, lifted state (Sales, Phase 10).** Three icon buttons per Sales row in a dedicated Actions column: `[$ DollarSign] [📎 Paperclip] [↩ Undo2]`. **Discoverability beats density** for an internal tool with workshop-staff users — explicit affordances on every row beats a hidden context menu. **Modal state is lifted to the table component**: `paymentRowId` / `billRowId` / `returnRowId` are three string-or-null slots at the table level (one slot per modal type, with `activeRowId` determining which row's data feeds the modal). The active modal's data is derived live via `sales.find(s => s.id === paymentRowId)` — same Phase 3.2 derive-from-id pattern that prevented stale-snapshot bugs in the detail modal. **Avoided**: per-row state (would have been three modals × N rows on every render). Discovered Phase 10 planning.

- **Bill upload preview via browser-native APIs (Phase 10).** `URL.createObjectURL(file)` produces a blob URL that an `<img>` (for image MIMEs) or `<embed type="application/pdf">` (for PDFs) renders without any server round-trip. The user confirms the right file is selected BEFORE the modal triggers `prepareUpload` → R2 PUT → `confirmUpload`. Cleanup via `URL.revokeObjectURL` on unmount or file replacement prevents the blob-URL pool from leaking across many uploads. **Fallback** for non-image / non-PDF types (which shouldn't reach this point — the schema rejects them — but render a "no preview available" notice for robustness). `BillPreview` lives in `src/components/` and is shared between `BillActionModal` (table action button path) and the form page (when Phase 10.5 adds an inline bill section). Discovered Phase 10 walkthrough Step 8 critical check.

- **Action modal dispatch via prop injection (Phase 10.5).** `PaymentActionModal` / `ReturnActionModal` accept an `onSave: (data) => Promise<SaveResult>` prop instead of switching on `entityType` internally; `BillActionModal` accepts optional `onAttach: (entityId, billId) => Promise<{ok}>` / `onDetach: (entityId) => Promise<{ok}>` props for Casting/Plating's `billId @unique` FK management (Sales/Purchases use the discriminator-only attachment and pass neither). The internal chain (`getBillForEntity` → optional `onDetach` → `softDeleteBill` → `prepareUpload` → R2 PUT → `confirmUpload` → optional `onAttach`) stays entity-agnostic. **Why prop injection over a `switch (entityType)` inside the modal**: each branch would import the entity-specific server actions, transitively dragging all four entities' action modules into every modal's bundle even when the rendered instance only uses one. Prop injection keeps the modal pure and pushes the action choice to the caller (where the imports are already local). **Phase 10.6 just wires casting/plating tables to dispatch the right actions** — no modal rebuilds. Cross-entity contract tests live in `payment-action-modal.test.tsx` / `bill-action-modal.test.tsx` parameterised via `describe.each(ENTITY_MATRIX)`; chain ordering verified via `callOrder: string[]` accumulator. Discovered Phase 10.5 planning.

- **Sales bill-in-form retrofit (pre-upload during save) (Phase 10.5).** The Sales form page (`/sales/new`, `/sales/[id]/edit`) includes an inline bill section between line items and totals: file picker → `BillPreview`. On submit, the chain runs **after** `createSale | updateSale` resolves with the entry's id (the bill needs `attachedToType="SALE"` + `attachedToId=savedSaleId` to be set at `prepareUpload` time). Order: `createSale → prepareUpload → R2 PUT → confirmUpload → navigate`. **Error semantics**: if the upload chain fails AFTER the entry is created, the entry **stays saved** (no rollback) and a banner directs the user to the row-level 📎 action modal for retry — rolling back the entry would punish a valid save for a recoverable network/storage failure. Edit mode adds NEW bills only (re-use the row-level modal for replace/remove, which already handles the soft-delete + re-upload transient state via the discriminator). **Purchases bill-in-form deferred to Phase 10.6**; the row-level 📎 modal covers the gap. Discovered Phase 10.5 walkthrough Steps 11-12.

- **Mirror-script string-literal leaks not caught by `tsc` (Phase 10.5).** When mirroring entity types via search-and-replace (the canonical Phase 9 mirror pattern), **string literals inside JSX props** (`entityType="sale"`) and **data object string values** (`attachedToType: "SALE"`) are valid in both source and target discriminated-union types — TypeScript accepts both because each is a legal member of the union. `tsc --noEmit` cannot catch the leak. Phase 10.5 found `entityType="sale"` literals leaked into `purchases-table.tsx` after the mirror, attached 4 orphan `SALE`-typed Bill rows to actual purchase IDs in production before the walkthrough caught it. **Defences** (apply after every mirror):
  - **(a)** Grep the target for source-entity literals: `grep -rni 'entityType="sale"' src/app/\(app\)/purchases/` should produce zero matches.
  - **(b)** Walkthrough must exercise a cross-system data path that verifies the discriminator value in the DB (e.g., `SELECT "attachedToType" FROM bills WHERE "attachedToId" = '<new entity id>'`) — not just the UI behaviour, which renders correctly on both branches.
  - **(c)** Cleanup query for any data corruption is part of the walkthrough script (Phase 10.5: scrubbed 4 SALE-typed bills attached to purchase IDs via `UPDATE bills SET "deletedAt" = NOW() WHERE "attachedToType" = 'SALE' AND "attachedToId" IN (<purchase ids>)`).
  - **(d)** Add an explicit regression-guard test in the mirrored entity's table test: assert every action-modal mount receives the correct `entityType` prop. Example in `purchases-table.test.tsx`. Discovered Phase 10.5 walkthrough.

### Phase 11 — Mobile + Visual restyle

- **Form line items use the `md:contents` trick to switch between stacked-mobile and flat-desktop layouts in one JSX tree (Phase 11.2).** Each line item is an outer `grid grid-cols-1 md:grid-cols-[1fr_80px_120px_120px_40px]` with three direct children: (a) Description div, (b) a wrapping inner div `grid grid-cols-[1fr_1fr_44px] md:contents`, and (c) a `md:hidden` mobile-only line-total row. The inner div contains four children — qty, rate, desktop-only line-total (`hidden md:flex`), and the × remove button. On mobile: the outer is single-column; the inner is a 3-col sub-grid placing qty/rate/× on row 2; the mobile-only line total appears as row 3. On md+: the inner div's `display: contents` makes it transparent to the grid layout, so its four visible children land in outer columns 2/3/4/5 — preserving the desktop horizontal layout. The mobile-only line-total row is hidden via `md:hidden`. **Why not separate desktop + mobile JSX trees**: would have required maintaining two copies of every line item input — error-prone with RHF `useFieldArray`'s field key bookkeeping, since each input has to keep its `register(...)` call. The single-tree pattern uses one input per slot and lets CSS decide layout. **Why not just `grid-cols-1` on mobile**: the qty/rate/× row needs a 3-column sub-grid on its own row, otherwise qty wraps full-width below description (consuming 3× the vertical space). The inner grid provides exactly that — and `md:contents` removes the wrapper from layout when desktop wants flat columns. Casting/Plating mirror with outer `[1fr_110px_130px_130px_40px]` (slightly wider for kg/rate displays). The pattern is documented as a citable convention in `CLAUDE.md §6` so future entity additions follow it.
